# FunBox 本地美食推荐产品设计方案 V1

> 版本：V1 草案
> 日期：2026-08-01
> 状态：待评审
> 定位：输入一个地址，就能知道附近有什么本地味道：图片、食材、口味、在哪吃、为什么推荐你。

## 1. 背景与问题

用户到了新城市、新片区，或者想换换口味时，常见的路径是打开地图搜"附近美食"，再逐个点开餐厅看评价，最后还要自己判断菜系、辣度、食材和价格是否合适。这个过程信息分散，容易踩坑：

| 现状 | 问题 |
| --- | --- |
| 搜索结果以餐厅为主 | 用户想先知道"吃什么"，而不是先看"去哪家店" |
| 图片与菜名分离 | 很多列表只有招牌和评分，看不到这道菜长什么样 |
| 口味不透明 | 麻辣、微辣、甜口没有统一表达，容易点错 |
| 食材不直观 | 不吃香菜、不吃内脏、清真等需求很难快速过滤 |
| 推荐理由缺失 | 只说"人气高"，不说为什么适合当前地址和口味 |
| 位置信息弱 | 距离、营业时间、适合场景分散在多个页面 |

FunBox 已经有 DeepSeek 能力（翻译、摘要、邮件代理共用 `DEEPSEEK_API_KEY`），可以低成本扩展出一个"本地美食推荐"工具，把地址理解、美食图片、食材、口味、推荐理由和位置信息串起来。

## 2. 对原始想法的补充

原始想法是"用户输入地址，推荐当地美食，展示图片、食材、口味"。在保留这个核心闭环的基础上，补充七点：

1. 地址是起点，位置要可理解。系统把地址解析为城市、区域、商圈、经纬度，推荐时明确标注"距你 1.2km、步行 15 分钟"。
2. 推荐以"菜品/小吃"为主体，而不是只推荐餐厅。一张美食卡回答五个问题：这是什么、什么味、用什么料、在哪吃、为什么适合你。
3. 口味和食材结构化。辣度、味型、主要食材、忌口标签统一建模，前端可筛选，DeepSeek 只基于这些事实生成文案。
4. 图片优先。每道菜必须有真实图片来源；图片缺失时显示占位态，不用 AI 编图或文字冒充。
5. 筛选和排序在结果页本地执行，不重复消耗 AI 额度；追问才触发新一轮生成。
6. 增加追问闭环。用户可以继续补一句"不要辣""人均 100 以内""更适合一个人吃"。
7. 距离、营业时间、评分来自数据快照，标注来源与更新时间，不承诺实时状态。

## 3. 产品目标与原则

### 3.1 产品目标

1. 输入地址或开启定位后，3 秒内看到第一批本地美食推荐（含图片、食材、口味、距离）。
2. 每条推荐必须有可解释的理由，且理由可追溯到数据字段。
3. 用户不需要先做复杂筛选就能完成"知道吃什么"这个动作。
4. 支持忌口与口味偏好，避免"推荐了但不敢吃"。

### 3.2 设计原则

- 先地址、后条件：地址是唯一必填项，其他偏好都可以后置。
- 先事实、后观点：图片、食材、口味、距离来自数据源，观点由 AI 基于事实生成。
- 少而准：默认返回 6-12 道，优先展示距离近、匹配当前口味的结果。
- 图片真实：不展示无来源或无法验证的美食图。
- 位置透明：标注"快照时间"与"数据来源"，不承诺实时排队、实时价格。

## 4. 目标用户与场景

| 用户 | 核心场景 | 产品应满足 |
| --- | --- | --- |
| 游客 | 刚到陌生城市，想知道酒店附近有什么本地特色 | 输入酒店地址，立刻看到附近代表菜品和推荐理由 |
| 本地人 | 住在某个片区，想找没吃过的小吃 | 按距离、菜系、辣度筛选，发现附近新选择 |
| 忌口用户 | 不吃辣、不吃香菜、清真、素食 | 用口味和食材标签过滤，避免踩雷 |
| 聚餐决策者 | 朋友来玩，需要选地方 | 按人均、适合场景（聚餐/夜宵/一人食）推荐 |
| 选择困难用户 | 看到一堆店不知道选哪个 | 用美食卡+"为什么推荐"快速缩小范围 |

首期建议选择 2-3 个城市做深度数据（如成都、重庆），先把"川渝本地味道"做透，验证后再扩展到全国。

## 5. 产品结构

### 5.1 入口

- 工具注册名：`food-recommendation`
- 工具名称：本地美食推荐
- 分类：生活
- 路由：`/tools/food-recommendation`
- 入口图标建议：`utensils`
- 状态先按 `coming-soon` 注册，上线后切换为 `available`

### 5.2 页面清单

| 页面 | 说明 |
| --- | --- |
| 地址与定位首页 | 自动定位、地址输入、快捷地址示例、热门需求标签 |
| 推荐结果页 | 摘要、排序、筛选、美食卡列表、换一批、追问入口 |
| 美食详情页 | 大图、口味、食材、做法、餐厅信息、推荐理由、去这里 |
| 筛选面板 | 底部抽屉：菜系、辣度、人均、距离、忌口 |
| 追问结果页 | 在上一轮结果基础上补充口味/预算/场景，重新生成 |
| 历史与收藏 | 登录用户查看最近查询、收藏美食与反馈记录 |

## 6. 核心流程

```text
进入工具
  → 自动定位，或输入"成都市武侯区玉林西路 12 号"
  → 地址解析为 城市/区域/商圈/经纬度
  → 后端按区域召回美食库候选
  → DeepSeek 基于候选的食材、口味、距离生成排序理由
  → 返回美食卡：图片、菜名、店名、距离、人均、口味、食材、理由
  → 用户点击卡片进入详情
  → 不满意时筛选或追问（不要辣/人均 100 内/适合一个人）
  → 满意时收藏、分享或去餐厅
```

## 7. 功能设计

### 7.1 地址与定位首页

- 顶部大搜索框支持地址自然语言，例如"成都市武侯区玉林""重庆解放碑附近"。
- 提供"使用当前位置"按钮；定位被拒绝时降级为手动输入，并保留最近一次地址。
- 提供快捷地址示例：当前位置、武侯祠、春熙路、解放碑等。
- 提供热门需求标签：不辣、人均 50 以内、朋友聚餐、夜宵。
- 生成按钮固定展示，输入为空时置灰。

### 7.2 推荐结果页

- 顶部摘要："为你在成都武侯区找到 12 道本地美食，优先推荐 2km 内、人均 60 左右的川味"。
- 排序条：综合 / 距离 / 人均 / 评分。
- 筛选入口：筛选按钮 + 已选条件计数，筛选只作用于当前结果池。
- 美食卡包含：
  - 真实美食图片
  - 菜名、菜系、辣度标签
  - 店名、距离、人均、评分
  - 主要食材（2-4 个 chips）
  - 一句"为什么推荐"
  - 有帮助 / 没帮助反馈
- 默认返回 6-12 道；底部提供"查看全部 / 换一批"。

### 7.3 美食详情页

- 顶部大图，带返回、收藏、分享。
- 基本信息：菜名、评分、人均、辣度、店名、地址、距离、营业时间。
- "这一口"模块：味型（麻辣鲜香、重油、回甜等）和口感描述。
- "主要食材"模块：食材 chips，支持点击查看忌口提示。
- "适合谁"模块：一人食、朋友聚餐、夜宵、带长辈等。
- "为什么推荐"模块：每条理由落到数据字段，例如"牛油锅底本地认可度高""距你 1.2km，步行 15 分钟""人均与评分均衡"。
- 底部操作：收藏、分享、去这里（V1 先跳外部地图/导航链接）。

### 7.4 筛选面板

- 菜系：火锅、川菜、小吃、面食、甜品、烧烤。
- 辣度：不辣、微辣、中辣、重辣。
- 人均：30 以内、30-60、60-100、100 以上。
- 距离：1km、3km、5km。
- 忌口：不吃辣、不吃香菜、清真、素食、不吃内脏。
- 所有选项非必选，默认不选；筛选后显示"查看 N 道"，支持重置与收起。

### 7.5 追问与调整

- 结果页和详情页保留快捷追问：不要辣、人均 100 以内、更适合一个人、换一家评分更高的。
- 追问沿用同一 `queryId`，后端在上一轮候选池基础上重新排序或召回。
- 追问结果保留"基于上一轮结果"标记，方便用户理解变化。

### 7.6 历史、收藏与反馈

- 登录用户保留最近 20 条查询与收藏。
- 美食卡提供"有帮助 / 没帮助 / 信息报错"反馈。
- 图片来源、营业时间、价格标注快照时间；失效信息进入后台审核队列。

## 8. AI 与数据架构

### 8.1 DeepSeek 复用方式

- 复用后端现有 `DEEPSEEK_API_KEY` 和 `config.DeepSeekConfig`。
- 新增 `backend/internal/food-recommendation/` 模块，DeepSeek 负责两件事：
  1. 把地址和自然语言需求解析为结构化条件（城市、区域、菜系、辣度、人均、场景、忌口）。
  2. 基于候选美食的结构化数据生成排序理由和一句话推荐。
- DeepSeek 不可用时降级为规则推荐：按距离、评分、人均权重排序，文案改为"距离近/评分高/符合预算"，并标记 `ai: "fallback"`。

### 8.2 美食数据源

| 阶段 | 数据源 | 说明 |
| --- | --- | --- |
| V1 | 结构化美食库（种子数据） | 2-3 个城市，每城 60-120 道代表菜；维护图片、食材、口味、店名、距离、人均 |
| V2 | 高德/腾讯地图 POI | 按区域召回真实餐厅、地址、距离、营业时间 |
| V3 | 商家页面/评价快照 | 评分、排队、价格、营业状态更新，接入外部链接 |

V1 美食库字段必须包含：

## 9. 接口设计

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/v1/food-recommendation/query` | 提交地址与偏好，返回推荐列表；复用现有限流中间件 |
| POST | `/api/v1/food-recommendation/locate` | 地址解析为城市/区域/经纬度，返回候选区域与中心点 |
| GET | `/api/v1/food-recommendation/catalog?city=&district=&q=` | 美食库搜索，用于补充候选和详情 |
| GET | `/api/v1/food-recommendation/queries/{queryId}` | 查询单次推荐结果 |
| POST | `/api/v1/food-recommendation/feedback` | 提交有帮助/没帮助/信息报错反馈 |
| GET | `/api/v1/food-recommendation/history` | 登录用户历史查询与收藏 |

说明：

- 查询与定位接口不强制登录，用 `withRateLimitedAPIPipeline` 限流；历史与收藏需要登录。
- 地址解析优先使用用户输入；定位只作为快捷入口，失败不影响主流程。
- DeepSeek 未配置时仍可返回规则推荐，响应中带 `ai: "fallback"`。
- 所有图片、价格、营业时间字段带 `source` 与 `updatedAt`，前端不自行声称实时数据。

## 10. 页面与交互设计

- 沿用 FunBox 现有视觉体系：浅蓝背景 `#EEF4FF`、白色表面、深色 `#151B3B` 重点、主色 `#4B6BFF`。
- 美食类增加暖色强调：辣度用橙红 `#FF6B5E`，评分用绿色 `#24B36B`，甜品/清淡用黄绿 `#C9F36A`。
- 内容区最大 430px 移动宽度，宽屏居中；卡片圆角不超过 16px，大图卡片不超过 20px。
- 美食卡图片建议 4:3 或 1:1，加载前显示灰色占位；图片缺失时显示"图片整理中"。
- 食材和忌口用 chips 表达，口味用"味型标签 + 一句话描述"，避免大段 AI 文本。
- 筛选面板使用底部抽屉，应用后列表即时更新、可重置可收起。
- 支持浅色与深色主题；320px、390px、430px 视口下文字不溢出、元素不重叠。

## 11. 状态与异常处理

| 场景 | 处理 |
| --- | --- |
| 定位被拒绝或失败 | 提示手动输入地址，保留最近一次地址 |
| 地址无法解析 | 提示"暂未识别该地址"，提供城市/区域示例 |
| 当前区域无数据 | 自动扩大到同城市，并提示"附近暂无，已为你扩展到全城" |
| DeepSeek 超时/失败 | 降级为规则推荐，返回 `ai: "fallback"` |
| 图片加载失败 | 显示占位图与"图片整理中"，不展示无来源图片 |
| 营业时间/价格过期 | 标记 `stale`，提示以商家页面为准 |
| 忌口过滤后无结果 | 显示空态与"重置筛选"，并推荐相近菜系 |
| 外部导航不可用 | 复制地址文本，并提示用户手动在地图 App 打开 |

## 12. 分期实施

### M1 地址输入 + 核心推荐

- 地址输入、当前位置、快捷示例
- 2-3 城结构化美食库（60-120 道/城）
- 推荐结果页与美食卡（图片、食材、口味、距离、理由）
- 美食详情页与"去这里"

### M2 筛选与追问

- 菜系/辣度/人均/距离/忌口筛选面板
- 排序、换一批、追问续聊
- 历史、收藏、有帮助/没帮助反馈

### M3 真实 POI 与实时状态

- 高德/腾讯地图 POI 接入
- 真实地址、距离、营业时间
- 评分、排队、价格快照更新
- 外部地图/导航链接

## 13. 成功指标

1. 输入地址到看到第一批结果，p90 不超过 3 秒（规则召回）或 5 秒（含 AI 文案）。
2. 首次使用无需展开筛选即可完成"知道吃什么"的比例不低于 60%。
3. 推荐结果页到详情页的打开率不低于 40%。
4. 用户对推荐"有帮助"反馈占比不低于 70%。
5. 美食图片加载成功率不低于 98%。
6. 筛选/追问功能使用率不低于推荐页访问量的 20%。

## 14. 明确不做

- 不做外卖、点单、下单、支付。
- 不做用户评价社区、达人种草、付费榜单。
- 不承诺"全城最好吃""绝对正宗"。
- 不使用无来源的图片、食材、口味数据。
- 不做药物、保健、特殊疗效类食物功效宣称。
- V1 不做实时排队、实时价格与导航路线规划。

## 15. 风险与开放问题

| 问题 | 当前建议 | 影响 |
| --- | --- | --- |
| 图片版权 | 使用带来源与署名的图片（如 Wikimedia），并在详情页标注 | 上线周期可控，后续可接商家图库 |
| 地图 POI 资质 | V1 用种子数据+文本地址，V2 再接入地图 API | 距离精度有限，用"步行约 15 分钟"替代精确导航 |
| 口味主观 | 口味表达统一为辣度+味型标签，不以个人评价替代事实 | 降低争议，但个性化需要用户反馈积累 |
| 商家信息时效 | 数据带快照时间与 `stale` 标记 | 需要后台定期维护与报错入口 |
| 城市扩展 | 首期只做 2-3 城深度数据 | 非首发城市体验不完整，先限制入口范围 |
| 定位权限 | 定位失败降级为手动输入 | 权限获取率影响自动定位比例，但不阻塞主流程 |
