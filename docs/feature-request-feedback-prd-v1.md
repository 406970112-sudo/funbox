# FunBox 功能建议与问题反馈一体化产品设计方案 V1

> 版本：V1 定稿草案
> 日期：2026-08-04
> 状态：待评审
> 定位：把首页搜索空态补上“去反馈”入口，将“功能建议”与现有“问题反馈”融合成一套真实数据闭环：用户提交、管理员处理、消息中心通知、用户查看结果。
> 交付口径：本期一次交付全部能力，不设分期、不设 V2 预留。

## 1. 背景与问题

当前首页搜索无结果时，面板只提供“清空关键词”和“在全部工具中查看”两个操作。用户搜不到想要的功能时，缺少一个把真实需求交回给产品团队的入口。

同时，现有“问题反馈”存在以下断点：

| 现状 | 断点 |
| --- | --- |
| 反馈入口只在“我的 > 账户” | 用户在搜索场景下产生需求时无法就近反馈 |
| 反馈只支持问题描述和截图 | 无法表达“我想要一个新功能”以及设计图 |
| 管理员后台只读 | 不能标记处理状态、写处理结果、回传给用户 |
| 消息中心只有聊天与互动通知 | 没有承载反馈处理结果的系统通知 |
| 反馈数据无用户侧视图 | 用户提交后只能等待，无法查看自己反馈的状态与结果 |

本次把这些断点合并为一个完整闭环：首页空态引导反馈、统一反馈中心、管理员处理、消息系统通知、用户已读与追溯。

## 2. 产品目标

### 2.1 核心目标

1. 让“搜不到”变成产品需求入口：首页搜索无结果时，用户一键进入功能建议，当前关键词自动带入。
2. 让反馈只有一个事实源：问题反馈与功能建议共用同一套数据库、接口、管理后台和用户消息通道，不维护两份数据。
3. 让处理结果真正回到用户：管理员提交处理结果后，用户立即在“消息 > 系统通知”看到，并可查看详情、标记已读。
4. 让每一条数据真实可追溯：用户提交、管理员处理、回复、已读状态全部来自真实数据库，不使用假数据、mock 数据或演示种子。

### 2.2 体验目标

- 从首页无结果到进入功能建议表单不超过 2 次点击。
- 功能建议表单在 1 分钟内可完成提交，失败不丢内容。
- 管理员处理反馈后，用户消息角标实时更新，不再依赖用户主动刷新。
- “我的反馈”与“消息 > 系统通知”展示同一条真实记录，状态一致。

### 2.3 一期非目标

以下能力不属于本期范围，避免把产品做重：

- 不做公开需求广场、投票、点赞排序。
- 不做反馈双方多轮聊天；本期为“用户提交 -> 管理员回复”的单轮结果闭环。
- 不做站外邮件或短信推送；结果只通过消息中心触达。
- 不做运营批量导入反馈。
- 不改动现有好友聊天、朋友圈、博客通知的数据结构。

## 3. 真实数据红线

这是本方案的第一约束，设计与实现都必须满足：

1. 前端不允许硬编码或内置任何反馈记录、管理员回复、处理状态、未读数、昵称、时间等演示数据。
2. 后端不允许向生产数据库 seed 示例反馈或示例回复；数据库只能保存用户真实提交和管理员真实处理产生的记录。
3. 首页搜索结果仍来自真实功能注册表与真实可玩游戏；空态的出现与否由真实过滤结果决定，不伪造无结果。
4. 功能建议表单的关键词带入来自用户本次真实搜索词，可编辑，不属于假数据。
5. 我的反馈、系统通知、未读数全部来自服务端接口；加载中、空状态、错误状态是唯一允许的兜底。
6. 设计图是用户真实上传文件，服务端校验类型、大小、数量后保存到私有目录，前端只展示服务端返回的真实图片。
7. 消息角标未读数由服务端根据 `reply_updated_at > user_read_at` 聚合返回，不允许客户端猜测计数。
8. 测试可以创建隔离的 SQLite 测试库写入测试数据，但生产库与测试库严格分离，测试数据不得进入用户可见页面。
9. 管理员回复按纯文本渲染，不执行 HTML；长度、权限、状态转换全部由服务端校验。
10. 用户提交、管理员处理、通知已读均走服务端事务或幂等写入，任何一步失败都不产生半条记录。

## 4. 现状盘点与融合策略

### 4.1 可复用能力

| 现有能力 | 复用方式 |
| --- | --- |
| `feedback_submissions` / `feedback_images` | 扩展字段承载功能建议、状态、回复与已读 |
| `POST /api/v1/feedback` | 增加 `kind`、`title`、`category`，保持问题反馈兼容 |
| 管理员反馈后台 | 从只读扩展为筛选、状态处理与结果回写 |
| 消息中心“互动通知”模式 | 新增“系统通知”页签，复用未读角标和跳转详情模式 |
| WebSocket 实时通道 | 新增 `feedback.resolved` 事件，刷新系统通知与未读数 |
| 现有主题、组件、路由体系 | 新页面全部沿用，不引入第二套设计 |

### 4.2 融合口径

- 产品命名统一为“反馈中心”：用户侧包含“问题反馈”与“功能建议”两个类型。
- 管理后台入口“问题反馈”改名为“反馈管理”，统一查看两类反馈。
- 消息中心“互动通知”保持社交语义，“系统通知”承载反馈处理结果，互不混淆。
- 反馈记录统一存储在同一张 `feedback_submissions` 表，通过 `kind` 区分问题与建议。

## 6. 核心流程

### 6.1 用户提建议

```text
首页搜索无结果
  -> 点击“去反馈”
  -> 未登录先登录，登录后带回关键词
  -> 功能建议表单（关键词预填到“功能名称”，可编辑）
  -> 填写标题、分类、描述，可选上传设计图
  -> 提交成功 -> 我的反馈显示“待处理”
  -> 管理员处理后 -> 消息 > 系统通知出现未读结果
  -> 打开详情标记已读 -> 我的反馈同步显示“已处理”
```

### 6.2 管理员处理

```text
管理后台 -> 反馈管理
  -> 选择问题或功能建议
  -> 查看用户、描述与设计图
  -> 点击“开始处理”置为处理中
  -> 填写处理结果 -> 提交
  -> 状态变为已处理，回复写入数据库
  -> 服务端向该用户推送 feedback.resolved
  -> 用户消息角标 +1，系统通知页签出现新记录
```

## 7. 功能设计

### 7.1 首页搜索空态“去反馈”

- 仅当真实搜索结果为空时展示，不改变现有搜索结果面板的数据来源。
- 空态保留现有图标、标题、副标题和两个按钮；“去反馈”放在按钮下方，使用整行入口，避免三个按钮挤在窄屏。
- 入口文案：“没有找到想要的功能？去反馈”，右侧副文案“告诉我们你想要的工具或游戏”，点击箭头进入功能建议。
- 从搜索空态进入时，把当前搜索词作为“功能名称”的预填值，用户可修改；未登录用户先进入登录页，登录成功后回到功能建议并保留关键词。
- 该入口在 Web 与移动端同时生效，继续沿用面板的卡片分隔线与主题色。

### 7.2 反馈中心与功能建议表单

- `/profile/feedback` 顶部增加“问题反馈 / 功能建议”分段切换；问题反馈保持现有表单，功能建议新增以下字段。
- “功能名称”必填，去除首尾空白后 5 至 40 个字符。
- “功能分类”必填，选项为“工具 / 游戏 / 社交 / 阅读 / 效率 / 其他”，用于后台筛选与统计。
- “功能描述”必填，去除首尾空白后 10 至 1000 个字符，多行输入并显示实时字数。
- “设计图”可选，最多 3 张，单张不超过 5 MB，仅支持 JPG、PNG、WebP；支持多选、预览、移除。
- 用户已登录，因此不需要填写联系方式；后台从真实用户信息读取昵称、账号、头像。
- 提交按钮在内容无效、正在上传、正在提交时禁用；失败保留表单内容并显示可恢复的中文错误。
- 提交成功后显示“功能建议已提交”，包含真实反馈 ID 与“待处理”状态，提供“查看我的反馈”和“返回首页”。

### 7.3 我的反馈

- 展示当前用户真实提交记录，按创建时间倒序分页。
- 每条展示类型徽标（问题/建议）、标题或描述摘要、提交时间、状态徽标、是否有回复。
- 点击进入详情：完整描述、设计图、管理员处理结果；未读结果打开后自动调用已读接口。
- 空状态只展示“还没有提交过反馈”的引导，不插入示例数据。

### 7.4 消息中心“系统通知”

- 消息页页签由两个变为三个：“聊天 / 互动通知 / 系统通知”。
- 系统通知仅展示 `status = resolved` 且存在管理员回复的真实反馈记录，按 `reply_updated_at` 倒序。
- 每条通知展示类型徽标、标题（“功能建议已处理”或“问题反馈已处理”）、回复摘要、时间与未读红点。
- 点击进入反馈结果详情并标记已读；未读数由服务端返回，消息 Tab 角标合并聊天、互动通知、系统通知三类未读。
- 管理员提交结果时，服务端通过 WebSocket 向用户推送 `feedback.resolved`，前端收到后刷新系统通知与未读数；WebSocket 不可用时，进入消息页仍通过 REST 拉取。

### 7.5 管理后台“反馈管理”

- 后台首页入口文案改为“反馈管理”，描述改为“查看并处理问题与功能建议”。
- 列表顶部提供类型筛选（全部/问题/建议）、状态筛选（全部/待处理/处理中/已处理）和关键词搜索；筛选项上的数量由服务端真实统计返回。
- 列表项展示类型徽标、状态徽标、用户昵称、标题或描述摘要、时间、图片数量；点击进入详情。
- 详情展示真实用户信息、提交时间、类型、标题、分类、完整描述、设计图预览与全屏查看。
- 处理动作：
  - “开始处理”：状态由待处理变为处理中。
  - “提交处理结果”：需填写 10 至 1000 字回复，状态变为已处理，记录处理人、处理时间，并清空该用户已读标记触发新通知。
  - 已处理记录仍可修改回复，修改后回复时间更新并再次产生未读通知。
- 非管理员访问后台接口返回 403；后端是最终权限边界。

## 8. 状态定义

所有状态由服务端 `feedback_submissions.status` 存储：

| 状态 | 含义 | 用户侧展示 | 管理员可操作 |
| --- | --- | --- | --- |
| `pending` | 待处理 | “待处理” | 开始处理 |
| `processing` | 处理中 | “处理中” | 提交处理结果 |
| `resolved` | 已处理 | “已处理”，展示回复 | 修改回复 |

`feedback_submissions.kind`：

| 值 | 含义 |
| --- | --- |
| `problem` | 问题反馈，兼容现有数据 |
| `feature_request` | 功能建议 |

## 9. 数据模型

复用现有 `feedback_submissions` 表，以幂等方式增加字段，不新建第二套反馈表：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | TEXT PK | 反馈 ID |
| `user_id` | TEXT NOT NULL | 提交用户，FK `users.id` |
| `kind` | TEXT NOT NULL | `problem` / `feature_request`，默认 `problem` |
| `title` | TEXT NULL | 功能建议标题；问题反馈为空 |
| `category` | TEXT NULL | 功能建议分类；问题反馈为空 |
| `description` | TEXT NOT NULL | 问题描述或功能描述 |
| `status` | TEXT NOT NULL | `pending` / `processing` / `resolved`，默认 `pending` |
| `admin_reply` | TEXT NULL | 管理员处理结果 |
| `admin_user_id` | TEXT NULL | 处理人，FK `users.id` |
| `processed_at` | INTEGER NULL | 首次完成处理时间（Unix 毫秒） |
| `reply_updated_at` | INTEGER NULL | 最近一次回复更新时间 |
| `user_read_at` | INTEGER NULL | 用户最近已读时间；未读为 NULL |
| `created_at` | INTEGER NOT NULL | 提交时间 |
| `updated_at` | INTEGER NOT NULL | 最近更新时间 |

图片继续使用 `feedback_images`，不区分问题截图或设计图，按 `sort_order` 展示。

建议新增索引：

```text
idx_feedback_kind_status_created(kind, status, created_at DESC)
idx_feedback_user_created(user_id, created_at DESC)
idx_feedback_status_reply(status, reply_updated_at DESC)
```

SQLite 没有 `ADD COLUMN IF NOT EXISTS`，迁移时先读取 `PRAGMA table_info` 再补列，保证老数据库升级幂等。

## 10. API 设计

### 10.1 用户接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/v1/feedback` | 提交反馈；`kind`、`title`、`category` 可选，兼容问题反馈 |
| `GET` | `/api/v1/feedback/mine?limit&offset` | 当前用户反馈列表，含状态、回复、未读 |
| `GET` | `/api/v1/feedback/{feedbackID}` | 当前用户自己的反馈详情 |
| `GET` | `/api/v1/feedback/notifications?limit&offset` | 已处理反馈通知列表，含 `unreadCount` |
| `POST` | `/api/v1/feedback/notifications/read` | 标记一条或全部反馈通知已读 |
| `GET` | `/api/v1/feedback/{feedbackID}/images/{imageID}` | 用户读取自己的反馈设计图/截图 |

### 10.2 管理员接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/v1/admin/feedback?kind&status&q&limit&offset` | 筛选、搜索、分页列表 |
| `POST` | `/api/v1/admin/feedback/{feedbackID}/resolve` | 置为处理中或提交处理结果 |
| `GET` | `/api/v1/admin/feedback/{feedbackID}/images/{imageID}` | 现有管理员取图接口保持不变 |

### 10.3 实时事件

```text
feedback.resolved
{
  "feedbackId": "...",
  "kind": "feature_request",
  "status": "resolved",
  "replyPreview": "已评估，计划加入工具分类"
}
```

服务端只向该反馈的用户推送；前端收到后刷新系统通知与未读数。

## 12. 安全与异常

- 提交、我的反馈、通知已读要求登录；管理员列表与处理要求 `admin` 角色。
- 服务端再次校验标题、分类、描述长度、图片数量、单图大小、真实图片类型与总请求大小。
- 处理结果必填 10 至 1000 字；状态转换白名单为 `pending -> processing -> resolved`。
- 用户图片接口必须校验反馈归属，不能通过他人反馈 ID 读取图片。
- 管理员回复与反馈内容按纯文本渲染，不执行 HTML，避免注入。
- 图片保存在私有存储目录，不注册公开静态目录；接口返回 Bearer 鉴权。
- 网络失败、登录失效、权限不足、内容过长均返回稳定错误码并映射为中文提示。
