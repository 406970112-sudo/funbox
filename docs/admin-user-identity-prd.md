# FunBox 管理后台「用户身份管理」产品需求文档

> 文档版本：V1.0  
> 状态：待评审  
> 适用端：管理后台 Web / 移动端  
> 目标版本：MVP

## 1. 需求背景

FunBox 当前已经存在四种用户角色：`normal`、`vip`、`svip`、`admin`，功能入口权限也可以按角色配置。但管理后台缺少用户管理入口，管理员无法查看用户列表，也无法将某个普通用户调整为 VIP 或 SVIP。

这会导致会员身份只能通过数据库或内部脚本修改，操作成本高、容易出错，也无法追踪是谁在什么时间做了调整。

本需求新增「用户身份管理」功能，让管理员可以在后台搜索用户、查看当前身份，并在普通用户、VIP、SVIP 之间调整用户身份。

## 2. 产品结论

本期将该能力定义为「用户身份管理」，不定义为通用「用户标签」。

- 用户身份是单选且互斥的：一个用户同一时间只能是普通用户、VIP 或 SVIP。
- 身份会直接影响该用户可访问的功能，应按权限变更处理。
- 页面中可以用彩色标签展示身份，但底层不是多选标签系统。
- `admin` 是后台权限角色，不等同于会员等级。本期管理员账号只展示、不可在该页面修改。

后续如果需要「活跃用户」「内容创作者」「渠道用户」等可同时存在的属性，再建设独立的多选运营标签能力。

## 3. 目标与范围

### 3.1 产品目标

1. 管理员可以快速找到目标用户并确认用户身份。
2. 管理员可以安全地将用户调整为普通用户、VIP 或 SVIP。
3. 身份调整后及时影响功能访问权限。
4. 每次调整可追溯，降低误操作和账号安全风险。

### 3.2 本期范围

- 管理后台新增「用户管理」入口。
- 用户列表、关键词搜索、身份筛选和分页。
- 用户详情摘要。
- 普通用户、VIP、SVIP 三种身份的单用户调整。
- 二次确认、结果反馈和并发冲突处理。
- 身份变更操作日志。
- 管理员账号保护规则。

### 3.3 非本期范围

- 批量调整用户身份。
- VIP/SVIP 付费购买、订单、退款和自动续费。
- 按日期自动到期或自动降级。
- 自定义会员等级。
- 多选运营标签。
- 在本页面新增、删除、封禁用户。
- 在本页面授予或撤销管理员权限。

## 4. 用户身份定义

| 身份 | 系统值 | 展示文案 | 含义 | 可由本页面调整 |
| --- | --- | --- | --- | --- |
| 普通用户 | `normal` | 普通用户 | 注册后的默认身份 | 是 |
| VIP | `vip` | VIP | 可访问配置给 VIP 的功能 | 是 |
| SVIP | `svip` | SVIP | 可访问配置给 SVIP 的功能 | 是 |
| 管理员 | `admin` | 管理员 | 拥有管理后台权限 | 否，仅展示 |

身份本身不隐含上下级继承关系。某功能是否对 VIP 或 SVIP 开放，仍以现有「入口权限」配置为准。例如，一个功能只勾选 VIP 时，不应默认让 SVIP 访问，除非权限产品另行定义继承规则。

## 5. 信息架构

管理后台首页新增入口：

```text
管理后台
```

入口卡片文案：

## 6. 页面设计

### 6.1 用户列表页

页面标题为「用户管理」，默认展示全部用户，按注册时间倒序排列。

#### 顶部区域

- 搜索框：支持手机号和昵称模糊搜索。
- 身份筛选：全部、普通用户、VIP、SVIP、管理员。
- 结果统计：例如「共 326 位用户」。
- 刷新按钮：重新获取当前查询结果。

#### 桌面端列表字段

| 字段 | 说明 |
| --- | --- |
| 用户 | 头像、昵称 |
| 账号 | 手机号脱敏展示，例如 `138****5678` |
| 当前身份 | 彩色身份标签 |
| 注册时间 | 精确到分钟 |
| 最近更新 | 用户资料或身份最近更新时间 |
| 操作 | 「调整身份」按钮；管理员账号显示「受保护」 |

#### 移动端列表字段

移动端使用纵向列表，每项展示头像、昵称、脱敏手机号、身份和注册时间。点击整行进入身份调整抽屉或独立详情页，不放置密集表格。

#### 空状态

- 没有任何用户：「暂无用户」。
- 搜索无结果：「没有找到符合条件的用户，请检查手机号或昵称」。
- 加载失败：展示错误说明和「重新加载」按钮。

### 6.2 身份调整面板

点击「调整身份」后，桌面端打开右侧抽屉，移动端打开底部面板或独立页面。

面板内容：

1. 用户摘要：头像、昵称、完整手机号、注册时间、当前身份。
2. 身份单选项：普通用户、VIP、SVIP。
3. 变更说明：非必填，最多 100 字，例如「活动赠送 30 天权益」。
4. 权限影响提示：展示新身份将按「入口权限」配置获得对应功能访问权。
5. 操作按钮：取消、确认调整。

管理员账号打开后只展示账号信息和提示：「管理员身份受保护，不能在用户管理中调整。如需变更后台权限，请使用独立的管理员授权流程。」

### 6.3 确认弹窗

只有选择了不同于当前身份的选项，确认按钮才可用。

确认文案示例：

```text
确认将“张三（138****5678）”从普通用户调整为 VIP？

调整后，该用户将按 VIP 身份重新计算可访问功能。
```

按钮：

- 次按钮：取消
- 主按钮：确认调整

从 VIP/SVIP 降级为普通用户时，主按钮使用警示样式，并补充：「用户可能立即失去部分功能访问权。」

## 7. 交互流程

### 7.1 正常调整流程

```text
进入用户管理
→ 搜索或筛选用户
→ 点击调整身份
→ 选择新身份
→ 填写可选说明
→ 二次确认
→ 后端校验管理员权限和用户最新身份
→ 保存身份与操作日志
→ 返回成功结果并刷新该用户
```

成功提示示例：「已将张三调整为 VIP」。

### 7.2 身份生效规则

- 后端保存成功即视为生效。
- 现有鉴权会在每次请求时读取用户最新数据，因此服务端权限应在下一次请求生效。
- 用户前端本地仍可能显示旧身份；客户端应在回到前台、重新进入受限功能或收到 403 时刷新 `/api/v1/auth/me` 与可见功能列表。
- 不强制用户退出登录，除非后续安全策略要求身份变更后使旧令牌失效。

### 7.3 并发与失败处理

- 用户不存在：提示「用户不存在或已删除」，关闭面板并刷新列表。
- 管理员权限失效：跳转个人页并提示「当前账号没有管理员权限」。
- 目标用户身份已被他人修改：提示最新身份，要求管理员重新确认。
- 重复提交同一身份：按幂等成功处理，不新增重复变更日志。
- 网络失败：保留当前选择和说明，允许重试。

## 8. 安全与权限规则

1. 所有列表、详情、修改和日志接口必须同时校验登录态与管理员身份。
2. 普通用户、VIP、SVIP 不得访问用户管理接口。
3. 本页面禁止把任何账号改为 `admin`，也禁止把 `admin` 改为会员身份。
4. 管理员不得修改自己的后台角色。
5. 后端必须使用白名单校验目标身份，只接受 `normal`、`vip`、`svip`。
6. 修改时同时提交客户端看到的旧身份，服务端不一致则返回冲突，防止覆盖他人刚完成的操作。
7. 日志不得记录密码、令牌、密保答案等敏感信息。
8. 手机号在列表中默认脱敏；仅在身份调整面板中按管理权限展示完整账号。

## 9. 操作日志

每次有效身份调整记录：

| 字段 | 说明 |
| --- | --- |
| `id` | 日志 ID |
| `target_user_id` | 被调整用户 ID |
| `operator_user_id` | 操作管理员 ID |
| `from_role` | 调整前身份 |
| `to_role` | 调整后身份 |
| `reason` | 变更说明，可为空 |
| `created_at` | 操作时间 |

一期日志可先用于后端审计；如果工期允许，在用户详情下增加「最近身份变更」区域，展示最近 10 条记录。

## 10. 接口建议

### 10.1 获取用户列表

`GET /api/v1/admin/users?q=&role=&limit=20&offset=0`

返回用户摘要、总数、分页信息。`q` 匹配手机号或昵称，`role` 为可选精确筛选。

### 10.2 获取用户详情

`GET /api/v1/admin/users/{userId}`

返回用户基础信息、当前身份及最近身份变更记录。

### 10.3 修改用户身份

`PATCH /api/v1/admin/users/{userId}/role`

请求示例：

```json
{
  "expectedRole": "normal",
  "role": "vip",
  "reason": "活动赠送权益"
}
```

成功返回更新后的用户摘要。建议错误码：

| HTTP 状态 | 错误码 | 场景 |
| --- | --- | --- |
| 400 | `invalid_role` | 目标身份不在允许范围 |
| 401 | `unauthorized` | 未登录或令牌失效 |
| 403 | `admin_required` | 非管理员访问 |
| 403 | `protected_admin_role` | 尝试修改管理员账号 |
| 404 | `user_not_found` | 目标用户不存在 |
| 409 | `role_changed` | 当前身份与 `expectedRole` 不一致 |

### 10.4 获取身份变更日志

`GET /api/v1/admin/users/{userId}/role-changes?limit=10&offset=0`

## 11. 数据设计建议

### 11.1 MVP

复用现有 `users.role` 字段，支持 `normal / vip / svip / admin`。新增 `user_role_changes` 表保存审计记录。

此方案改动小，可直接接入现有按身份控制功能入口的逻辑。

### 11.2 后续演进

当前 `role` 同时承载会员身份和后台权限，长期容易产生歧义。建议在需要多管理员或付费会员体系前拆分为：

- `users.membership_tier`：`normal / vip / svip`
- `users.system_role`：`user / admin`
- 可选 `membership_expires_at`：会员到期时间

届时一个管理员也可以同时拥有明确的会员等级，后台权限与用户权益不会互相覆盖。

## 12. 埋点建议

| 事件 | 触发时机 | 关键参数 |
| --- | --- | --- |
| `admin_user_list_view` | 打开用户管理 | 管理员 ID |
| `admin_user_search` | 执行搜索 | 查询类型、结果数 |
| `admin_role_change_open` | 打开身份调整 | 当前身份 |
| `admin_role_change_confirm` | 确认提交 | 原身份、目标身份 |
| `admin_role_change_success` | 保存成功 | 原身份、目标身份 |
| `admin_role_change_failed` | 保存失败 | 错误码 |

埋点中不要上传完整手机号和变更说明原文。

## 13. 验收标准

### 13.1 功能验收

- 管理员可以打开用户管理页并分页查看用户。
- 支持按手机号或昵称搜索，支持按身份筛选。
- 管理员可以在普通用户、VIP、SVIP 之间相互调整。
- 不允许选择当前身份作为一次新的变更。
- 不允许通过页面或接口修改管理员账号身份。
- 调整成功后，列表和详情立即显示新身份。
- 调整后的用户在下一次权限请求时按新身份获得功能列表。
- 每次有效变更都有完整操作日志。
- 并发修改时不会静默覆盖最新身份。

### 13.2 体验验收

- 桌面端和移动端都能完成搜索、查看和修改流程。
- 列表加载、空结果、失败、保存中、保存成功均有明确状态。
- 保存过程中按钮不可重复点击。
- 降级操作具有明确警示，但不使用阻断性高风险文案。
- 所有手机号在列表页默认脱敏。

### 13.3 测试重点

- 四种身份的筛选和展示。
- normal、vip、svip 的全部双向切换组合。
- 非管理员越权访问和直接调用接口。
- 管理员账号保护。
- 两名管理员同时修改同一用户。
- 修改后当前在线用户的权限刷新。
- 搜索边界、分页边界和空结果。
- 操作日志与实际变更一致。

## 14. 上线顺序

1. 后端增加用户列表、身份修改和审计日志能力，并完成接口测试。
2. 管理后台增加「用户管理」入口、列表和身份调整面板。
3. 用户端补充身份与可见功能的刷新机制。
4. 使用测试账号验证升级、降级、管理员保护和并发冲突。
5. 小范围开放给管理员使用，观察失败率与误操作情况后全量开放。

## 15. 待评审问题

1. VIP/SVIP 是否未来需要有效期？如果需要，本期是否先预留到期时间展示位。
2. SVIP 是否应自动继承 VIP 可访问的全部功能？当前权限模型是分别配置，需要产品明确。
3. 是否需要在用户端「我的」页面展示身份标签和对应权益说明。
4. 身份调整是否必须填写原因，还是仅降级时必填。
5. 管理员授权是否需要单独建设更严格的双人确认流程。
