# FunBox 冰箱剩菜管家（剩菜与外卖管理）产品设计方案 V1

> 版本：V1 完整一期  
> 日期：2026-08-06  
> 状态：待评审  
> 定位：把冰箱里的剩菜、外卖和已开封食品变成一张真实可执行的“优先吃掉”清单，并根据冰箱里的真实食材给出可解释的今晚建议。

## 1. 背景与问题

冰箱里最容易发生的不是“没东西吃”，而是“不知道有什么、不知道哪件先过期、不知道今晚吃什么”。

| 现状 | 问题 |
| --- | --- |
| 靠记忆记住剩菜 | 昨天、前天的菜被忘在角落，等想起来时已经不能吃 |
| 凭感觉判断期限 | 不知道哪件今天必须吃，哪件还能放两天 |
| 外卖剩菜反复热 | 是否加热过、还能热几次，没有记录 |
| 食材分散 | 冰箱里明明有西红柿、鸡蛋、土豆和午餐肉，却想不起能做什么 |
| 吃完/丢弃无反馈 | 浪费了多少、真正吃完多少，没有真实记录 |

FunBox 已有账号、JWT、SQLite、工具注册、主题系统和通知能力。本功能复用这些基础能力，不需要引入新的第三方服务。

## 2. 对原始想法的补充

原始想法是：记录冰箱里的剩菜名称、放入时间、预计食用期限、照片、是否加热过和剩余分量；首页显示“优先吃掉”，并根据冰箱现有食材建议今晚做西红柿炒鸡蛋和土豆午餐肉。

在此基础上一期补齐十二点：

1. 记录对象扩展为“剩菜、外卖、开封食品、生鲜食材”四类，所有记录都必须由用户真实创建。
2. 每条记录保存真实入冰箱时间，默认使用当前服务器时间，用户可修改为真实时间。
3. “预计食用期限”必填，由用户选择真实日期时间；系统提供“今晚、明天、两天内”快捷选项，但快捷选项只生成具体的截止时间，不代替用户判断。
4. 照片必须是用户从相机或相册上传的真实照片，最多 3 张，不提供占位图。
5. 加热状态记录为“未加热、已加热 1 次、已加热 2 次及以上”，并在详情页提供“加热一下”操作。
6. 剩余分量使用“完整、三分之二、一半、少量、一口”快速选项，并可补充真实文字，例如“约 1 碗”。
7. 首页“优先吃掉”只来自用户真实创建且状态为 `active` 的记录，按到期时间从早到晚排序。
8. “今晚建议”使用冰箱里的真实食材标签和真实菜谱库做确定性匹配，不调用 AI 编造菜谱。
9. 建议卡片展示“用到了哪些真实冰箱记录”和“还缺哪些食材”，不会假装所有食材都已存在。
10. 每条记录支持“吃完、丢弃、加热”三个真实动作，动作写入事件流并进入历史统计。
11. 到期提醒使用服务器真实时间和用户真实授权状态；未授权时只显示应用内待办，不显示“已通知”。
12. 所有页面、接口、规则、通知、统计和导出在本期一次完成，不设二期。

## 3. 产品目标与设计原则

### 3.1 产品目标

1. 用户 30 秒内完成一条冰箱记录的新增。
2. 用户每天打开首页，能清楚知道“今天必须吃哪几件”。
3. “今晚建议”里的每一条都能追溯到真实冰箱记录和真实菜谱来源。
4. 所有数字都可解释、可追责：来源是用户录入、系统时间或公开菜谱库。

### 3.2 设计原则

- 真实优先：首启为空，不预置剩菜、外卖、食材或统计。
- 用户决策：系统只按真实到期时间排序和提示，不替用户判断“还能不能吃”。
- 可解释：优先顺序、今晚建议、提醒时间都展示计算依据。
- 克制自动：菜谱匹配只使用用户记录过的真实食材，不自动创建缺失食材。
- 一期全量：所有核心页面、动作、提醒、统计、导出一次完成。
- 隐私克制：数据只属于当前用户，不公开、不排行、不进入社交动态。
- 风格一致：沿用 FunBox 浅蓝画布、白色表面、深色文字、蓝色主操作和现有 320-430px 移动端布局。

## 4. 目标用户与场景

| 用户 | 核心场景 | 产品应满足 |
| --- | --- | --- |
| 上班族 | 晚饭后把剩菜放进冰箱，第二天忘了是什么 | 拍照并记录名称、时间和期限，首页按到期时间提醒 |
| 外卖用户 | 点了外卖吃不完，剩菜和打包盒混在一起 | 区分外卖来源，记录开封时间、加热状态和剩余分量 |
| 家庭用户 | 冰箱里食材多，不知道今晚做什么 | 用真实食材匹配真实菜谱，展示匹配度和缺少项 |
| 爱惜食物用户 | 想减少浪费，记录吃完和丢弃情况 | 吃完、丢弃动作进入真实历史，统计浪费变化 |
| 临时出差用户 | 离开前需要处理临期食品 | 临期列表、到期提醒和“今天优先吃”帮助快速处理 |


## 6. 功能设计

### 6.1 首页“优先吃掉”

- 顶部展示真实摘要：今天必吃、24 小时内到期、已过期数量，全部由当前用户 `active` 记录计算。
- “优先吃掉”分组：
  - 已过期：`expected_consume_at < server_now`，红色；
  - 今天：今天 23:59 前到期，金色；
  - 明天：明天 23:59 前到期，薄荷色；
  - 冷冻：进入冷冻但仍有食用计划的记录，蓝色。
- 每条记录展示真实照片缩略图、名称、到期时间、加热状态、剩余分量和来源标签。
- 没有 `active` 记录时显示真实空态，不展示占位剩菜。
- 首页下方展示“今晚建议”摘要，最多 3 条；没有可匹配菜谱时显示“还没有可匹配的冰箱食材”，不伪造建议。
- 快捷入口：添加记录、查看冰箱库存、查看历史。

### 6.2 添加/编辑记录

#### 记录类型

- 剩菜：自做饭菜，必填名称、入冰箱时间、预计食用期限、剩余分量。
- 外卖：必填名称和入冰箱时间；可填写商家名称，用于首页展示“昨天点的 XX 外卖”。
- 开封食品：可填写包装上标注的“开封后 X 天内食用”和真实开封日期。
- 生鲜食材：用于“今晚建议”匹配，例如西红柿、鸡蛋、土豆、午餐肉。

#### 字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 名称 | 是 | 1-40 个字符，去除首尾空格 |
| 来源/商家 | 否 | 外卖商家或购买渠道，最多 30 字符 |
| 入冰箱时间 | 是 | 默认当前服务器时间，可修改 |
| 预计食用期限 | 是 | 用户选择真实日期时间，或选择“今晚/明天/两天内”快捷项 |
| 存放位置 | 否 | 冷藏、冷冻、冰箱门、冷藏抽屉、自定义位置 |
| 剩余分量 | 是 | 完整/三分之二/一半/少量/一口，可补充真实文字 |
| 加热状态 | 是 | 未加热/已加热 1 次/已加热 2 次及以上 |
| 照片 | 否 | 相机或相册上传，最多 3 张，第一张为封面 |
| 食材标签 | 否 | 用于菜谱匹配，例如西红柿、鸡蛋、土豆、午餐肉、米饭、面条 |
| 成本/金额 | 否 | 用户真实填写的外卖金额或食材成本，单位分 |
| 备注 | 否 | 最多 60 字符，例如“有点咸，加热时加水” |

校验规则：

- 名称不能为空，不能与当前用户未处理记录重名。
- 入冰箱时间不能晚于当前服务器时间超过 5 分钟。
- 预计食用期限必须晚于入冰箱时间；选择“冷冻”时可填写冷冻日期。
- 剩余分量不能为 0%，为 0% 时提示先标记“吃完”而不是保存记录。
- 食材标签使用受控词表，禁止系统根据名称自动猜测。

### 6.3 记录详情

- 展示真实照片、名称、来源、入冰箱时间、预计食用期限、存放位置、剩余分量、加热状态、食材标签、成本金额和备注。
- 剩余时间使用 `expected_consume_at - server_now` 计算，前端不自行猜测。
- 主操作：
  - “加热一下”：`reheat_count + 1`，写入 `reheated` 事件；
  - “标记吃完”：写入 `eaten_at` 和 `eaten` 事件；
  - “丢弃”：必须选择原因，写入 `discarded_at` 和 `discarded` 事件。
- 已过期记录显示红色提示“已超过预计食用期限”，但系统不自动删除。
- 事件时间线展示创建、加热、吃完、丢弃的真实服务器时间。

### 6.4 今晚建议

#### 菜谱匹配

真实菜谱库中的每条菜谱包含：

```text
recipe_id
name
main_ingredients: [{ keyword, label, quantity }]
seasonings: [{ keyword, label }]
estimated_minutes
steps
source
```

匹配规则：

- 只使用当前用户 `status=active` 且 `remaining > 0` 的冰箱记录。
- 一条冰箱记录命中菜谱主食材时，只要其名称或食材标签包含菜谱关键词即算命中。
- 命中数量为 0 的菜谱不展示。
- 匹配度 = 命中主食材数量 / 菜谱主食材总数 × 100。
- 排序分 = 匹配度 + 临期加成；若建议中使用了 24 小时内到期的真实食材，每条加 10 分，最多加 30 分。
- 调味料不参与匹配，但菜谱卡片中可展示为“常备调料”。

#### 建议卡片

- 展示真实菜谱名称、匹配度、预计用时、来源。
- “用到了你的冰箱”列表展示命中的真实记录名称和剩余分量。
- “还缺”列表展示菜谱要求但当前没有匹配到的食材；没有缺项时显示“冰箱食材已齐”。
- 用户可展开查看完整真实菜谱步骤。
- 用户可“复制缺料清单”，复制内容来自菜谱库和当前冰箱记录的差集。
- 不自动创建任何食材记录、不自动跳转购买、不假装已拥有缺失食材。

### 6.5 历史与统计

- 历史列表只包含真实 `eaten` 和 `discarded` 事件。
- 统计口径：
  - 本周吃完数：`eaten` 事件数；
  - 本周丢弃数：`discarded` 事件数；
  - 避免浪费金额：已吃完记录中用户填写成本之和；
  - 浪费金额：已丢弃记录中用户填写成本之和。
- 30 天趋势图按真实事件日期聚合；无数据时显示空态，不绘制占位曲线。
- 支持按状态、时间范围筛选。
- 支持导出当前用户 CSV/JSON。
- 支持清空全部数据，需二次确认，清空后接口不再返回已删除记录。

### 6.6 设置与通知

- 提醒规则由用户配置：
  - 到期前 2 小时；
  - 当天 09:00；
  - 每天 19:00 汇总当天未处理临期记录。
- 通知权限页显示系统真实授权状态：已开启、未开启、待授权。
- 未授权时首页保留“优先吃掉”和应用内待办，不提示“已通知”。
- 数据来源说明页列出：
  - 冰箱记录：用户真实录入；
  - 照片：用户真实上传；
  - 时间：服务器当前时间；
  - 菜谱：版本化真实菜谱库，每条带来源；
  - 统计：SQL 聚合真实事件。

## 7. 真实数据方案

### 7.1 数据来源

| 数据 | 来源 | 展示规则 |
| --- | --- | --- |
| 名称、来源、位置、分量、备注 | 用户输入 | 原样保存，仅去除首尾空格 |
| 入冰箱时间 | 用户选择，默认服务器时间 | 与服务器时间比较，不保存相对文字 |
| 预计食用期限 | 用户选择具体日期时间 | 快捷项只生成具体截止时间 |
| 照片 | 用户上传 | 只展示用户真实照片，不提供占位图 |
| 加热状态 | 用户选择或“加热一下”动作 | 每次动作写入事件流 |
| 食材标签 | 用户选择受控词表 | 系统不根据名称自动猜测 |
| 菜谱 | 版本化真实菜谱库 | 每条菜谱带 `source`，不允许运行时生成 |
| 提醒状态 | 服务器时间 + 用户授权状态 | 未授权不显示“已通知” |
| 统计 | SQL 聚合真实事件 | 无事件时为空态 |

### 7.2 计算规则

```text
剩余小时 = expected_consume_at - server_now
优先顺序 = expected_consume_at 升序
匹配度 = 命中主食材数 / 菜谱主食材总数 × 100
排序分 = 匹配度 + min(临期食材数 × 10, 30)
避免浪费金额 = sum(已吃完记录.cost_cents)
浪费金额 = sum(已丢弃记录.cost_cents)
```

### 7.3 无 mock 保障

- 首次进入为空态，不预置任何剩菜、外卖、食材或统计。
- 不内置示例菜名、示例商家、示例照片或示例金额。
- 不根据名称自动生成食材标签。
- 不根据冰箱记录自动创建缺失食材。
- 不用 AI 编造菜谱、到期时间或“还能不能吃”的结论。
- 开发测试数据与生产数据物理隔离，禁止测试种子写入生产环境。
- 设计稿中的录入后界面只表达界面位置，正式产品首启为空。

| GET | `/api/v1/leftover-manager/history` | 历史记录与统计 |
| GET/PUT | `/api/v1/leftover-manager/settings` | 提醒与数据设置 |
| GET | `/api/v1/leftover-manager/export?format=csv\|json` | 导出当前用户数据 |
| DELETE | `/api/v1/leftover-manager/data` | 清空当前用户全部数据 |

### 8.3 状态机

```text
active --标记吃完--> eaten
active --丢弃--> discarded
active --加热--> active (reheat_count + 1)
active --编辑--> active (updated_at 更新)
eaten / discarded --仅可删除，不自动回退
```

## 9. 状态与异常处理

| 场景 | 处理 |
| --- | --- |
| 首次进入且无记录 | 真实空态，提供添加记录入口 |
| 没有可匹配菜谱 | 今晚建议显示“还没有可匹配的冰箱食材” |
| 照片上传失败 | 保留其他字段，提示重试，不自动使用占位图 |
| 通知未授权 | 设置页显示真实状态，首页继续提供应用内待办 |
| 服务器时间不可用 | 接口返回 `serverNow` 失败时，前端禁止计算倒计时 |
| 同步失败 | 保留本机真实数据，顶部提示“同步失败，已使用本机数据” |
| 删除/清空 | 删除前二次确认；清空前要求再次确认 |
| 菜谱库加载失败 | 今晚建议隐藏，首页其余功能正常 |

## 10. 技术方案

- 前端新增 `frontend/features/tools/leftover-manager-screen.tsx`，在 `ToolDetailScreen` 增加路由映射。
- 前端模型与 API 客户端新增 `frontend/types/leftover-manager.ts` 和 `frontend/lib/leftover-manager-api.ts`。
- 本机存储新增 Web / Native 实现；未登录可完整使用本机数据，登录后与账号同步。
- 后端新增 `backend/internal/leftovermanager/` 模块和 `backend/internal/httpapi/leftover_manager_handlers.go`。
- 菜谱库作为版本化 JSON 入库，带 `source` 字段；运行时不调用模型生成菜谱。
- 照片沿用现有上传目录和鉴权方式，不写入公开路径。
- 到期扫描任务每分钟检查 `active` 且 `expected_consume_at <= now` 的记录，写入提醒事件。
- 通知使用 `expo-notifications`，只发送由服务器真实时间计算的提醒；未授权状态写回设置页。
- 新增 Node 测试覆盖匹配引擎、空态、状态机、统计、导出和清空逻辑。

## 11. 一期范围与验收标准

### 11.1 一期交付清单

- 首页“优先吃掉”：真实排序、临期统计、空态、快捷入口。
- 添加/编辑：四种类型、全部字段、校验、照片上传。
- 记录详情：照片、字段、加热、吃完、丢弃、事件时间线。
- 今晚建议：真实菜谱匹配、匹配度、缺少项、菜谱详情、复制缺料清单。
- 冰箱库存：分类、搜索、位置筛选。
- 历史与统计：真实事件、30 天趋势、导出、清空。
- 设置与通知：提醒规则、通知权限真实状态、数据来源说明。
- 前后端测试、类型检查、lint 全部通过。

### 11.2 验收标准

1. 首次进入为空态，不出现任何预置剩菜、外卖、食材、照片或统计。
2. 新增记录必须包含名称、入冰箱时间、预计食用期限、剩余分量和加热状态。
3. 照片必须是用户上传的真实照片，系统中不存在占位图。
4. “优先吃掉”列表只来自用户真实 `active` 记录，按到期时间升序。
5. “今晚建议”只匹配真实冰箱记录，命中为 0 时隐藏。
6. 建议卡片必须展示命中的真实记录和缺少项，不允许假装食材齐全。
7. 到期提醒使用服务器真实时间，未授权时不显示“已通知”。
8. 吃完、丢弃、加热动作写入事件流，历史统计只汇总真实事件。
9. 导出、单条删除、清空全部数据均可用，清空后接口不再返回已删除数据。
10. 320px、390px、430px 视口无文字溢出、无元素重叠。
11. Go 测试、前端 Node 测试、TypeScript 检查与 lint 全部通过。

## 12. 明确不做

- 不做 AI 判断“这盘菜还能不能吃”。
- 不做 OCR 识别外卖小票或自动识别食材。
- 不做系统自动创建缺失食材或自动下单。
- 不做家庭共享冰箱、好友排行榜或公开动态。
- 不做会员权益差异。
- 不做二期拆分；所有页面、接口、规则、通知和统计一期一次交付。

## 13. 风险与决策

| 风险 | 决策 |
| --- | --- |
| 用户忘记填预计期限 | 非冷冻记录必填期限，快捷项只生成具体时间 |
| 菜谱建议像“猜的” | 只使用真实菜谱库和真实冰箱记录，展示匹配依据 |
| 用户不记录食材标签导致无法匹配 | 名称包含关键词也可命中，不依赖唯一标签 |
| 照片过大或上传失败 | 压缩后上传，失败保留字段并提示重试 |
| 到期时间跨设备不一致 | 所有计算以服务器 `server_now` 为准 |
| 通知权限被关闭 | 显示真实状态，首页应用内待办继续可用 |
| 用户误点丢弃 | 丢弃需选择原因，删除与清空二次确认 |

## 14. 成功指标

1. 一条冰箱记录从进入页面到保存完成不超过 30 秒。
2. 首页“优先吃掉”中每一条都能追溯到用户真实创建记录。
3. “今晚建议”出现时，命中食材覆盖率 100% 可解释。
4. 记录状态变化后，历史与首页在 1 秒内保持一致。
5. 无 mock 校验：生产环境种子数据、演示记录和模拟统计数量为 0。
