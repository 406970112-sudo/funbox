# 打牌记分功能产品与技术设计

日期：2026-07-31
状态：待最终确认
适用项目：Funbox

## 1. 背景与目标

打牌过程中经常出现没有现金、零钱不够或不方便当场转账的情况。该功能用于替代纸笔和临时群聊记账，让同一牌局中的玩家在各自设备上记录每局得失分，系统实时汇总总分，并在牌局结束后按约定的“每分金额”生成结算方案。

首版目标：

- 支持房主创建多人记分房并通过二维码或房间号邀请玩家。
- 支持未注册玩家以临时昵称快速加入，房主必须登录。
- 每位玩家只提交自己的本局增减分，所有玩家共同确认后计入总分。
- 服务端强制校验本局所有增减分之和为 0，避免记漏或记重。
- 实时同步本局状态、累计分数、排名和折算金额。
- 牌局结束后生成真实最少笔数的转账方案，但不直接发起支付。
- 视觉和交互保持 Funbox 现有风格，并同时支持浅色、深色和 Web。

“本局分数”明确指某一小局结束后玩家的分数变化，例如 `+12` 或 `-5`，不是玩家的起始分数。所有玩家起始累计分数均为 `0`。

## 2. 范围与非目标

### 2.1 首版范围

- 通用记分模式，不绑定斗地主、麻将、掼蛋等具体规则。
- 2 至 8 人的实时多人房间。
- 整数分数和整数“分/每分”的金额换算，避免浮点误差。
- 逐局记分、全员确认、历史记录、冲正、结束结算。
- 房主历史牌局可回看；临时玩家可在房间有效期内重连。

### 2.2 后续扩展

- 斗地主、麻将、掼蛋等规则模板。
- 模板根据赢家、倍数、角色等输入自动计算各玩家增减分。
- 常用玩家、固定牌友群、战绩统计和模板收藏。
- 分享结算图片或长期战绩卡片。

规则模板只能产出标准化的 `score_entries`，后续仍走同一套零和校验、确认、累计和结算流程，避免为每种玩法重复建设底层能力。

### 2.3 不在首版范围

- 微信、支付宝或银行卡真实支付。
- 房主代替其他在线玩家填分或强制确认。
- 完全离线的点对点同步。
- 现金借贷、抽水、信用额度或催款。
- 具体牌类规则的自动裁定。

## 3. 用户角色与权限

### 3.1 房主

- 必须使用 Funbox 账号登录后创建房间。
- 可配置房间名称、人数上限、每分金额和记分模式。
- 可展示邀请二维码、房间号并开始牌局。
- 可发起新一局、取消尚未确认的一局、结束牌局。
- 可在两局之间移除玩家；已产生的历史得分仍保留并参与结算。
- 不可修改其他玩家的分数，不可替其他玩家确认，不可篡改已确认记录。

### 3.2 临时玩家

- 通过二维码或 6 位房间号进入 Web/App 加入页。
- 输入 1 至 12 个字符的房内唯一昵称后加入，无需注册。
- 仅能提交和修改自己的当前局分数，并确认当前局。
- 可查看房间中所有玩家、本局提交状态、已确认历史和结算结果。
- 获得仅对当前房间和当前参与者有效的签名临时令牌。

### 3.3 活跃参与者集合

每局开始时冻结本局参与者名单。只有该名单中的玩家需要提交和确认。玩家断线不会自动退出本局；房主只能取消该未确认局，不能绕过断线玩家强制结算该局。

## 4. 核心产品流程

### 4.1 创建房间

1. 房主从“工具”进入“打牌记分”。
2. 选择“创建房间”。未登录时先进入现有登录流程，登录成功后返回创建页。
3. 设置房间名称、人数上限和每分金额。默认值为 4 人、`¥0.50/分`。
4. 记分模式首版固定为“通用记分”，界面保留规则模板入口但标注为后续能力。
5. 创建成功后进入等候页，展示二维码、6 位房间号和已加入玩家。
6. 至少 2 人加入后，房主可开始牌局。

每分金额在牌局开始后锁定。若要更换换算比例，需结束当前房间并新建房间，避免历史金额口径变化。

### 4.2 加入房间

1. 玩家扫描二维码，优先打开 App，未安装时落到 Web 加入页；也可手动输入房间号。
2. 服务端校验房间存在、未结束、未满员且加入频率正常。
3. 玩家输入临时昵称；昵称重复时提示更换。
4. 加入成功后服务端签发房间级临时令牌，客户端安全保存并直接进入房间。
5. 刷新、切换网络或短暂断线时使用该令牌恢复原参与者身份，不重复占位。

### 4.3 逐局记分

1. 房主点击“开始第 N 局”，服务端冻结本局参与者集合。
2. 每位玩家在自己的设备上填写整数增减分，正分可直接输入数字，负分输入负号；`0` 允许提交。
3. 提交后仍可在进入确认阶段前修改自己的分数。
4. 所有人提交后，服务端计算本局合计：
   - 合计不为 `0`：显示“本局还差 +X/-X 分”，所有人可核对并各自修改自己的记录。
   - 合计为 `0`：进入确认阶段，展示完整分数明细和本局对累计分数的影响。
5. 所有人确认后，本局原子提交并计入累计分数。
6. 客户端播放轻量成功反馈，房主可发起下一局。

累计分数、排名和折算金额只使用已确认局。未确认局不会影响牌桌总榜。

### 4.4 错分修正

已确认局不可直接编辑或删除。发现错误时，由房主从该局历史发起“冲正”：

1. 系统创建一条关联原局的修正局，并预填相反分数。
2. 所有当前相关玩家查看修正原因和影响。
3. 修正局继续执行零和校验和全员确认。
4. 修正局确认后抵消原记录；需要录入正确结果时再新增一局。

这样可以完整保留审计链，避免牌局结束时因历史被静默修改产生争议。

### 4.5 结束与结算

1. 房主在没有待确认局时点击“结束牌局”。
2. 服务端冻结房间，生成每位玩家的最终分数和金额。
3. 系统基于净金额计算真实最少笔数转账方案。
4. 结算页展示“谁向谁转多少钱”、总局数、最终排名和历史明细。
5. 所有玩家可查看结果；首版只给出建议，不触发支付。

若所有人净额均为 `0`，结算页显示“本场已平账，无需转账”。

## 5. 页面与交互设计

### 5.1 信息架构

- 工具入口：在现有工具注册表中增加“打牌记分”，沿用动态工具路由。
- 首页：最近未结束房间、创建房间、加入房间。
- 创建页：基础配置和创建主按钮。
- 等候页：房间二维码、房间号、玩家列表、开始牌局。
- 记分页：房间摘要、累计榜、本局录入、提交/确认状态、历史入口。
- 结算页：最终排行、最少转账方案、逐局历史。
- 历史页：房主的已结束房间列表和详情。

不制作独立营销落地页，打开工具后直接进入可操作界面。

### 5.2 现有风格一致性

实现时必须复用现有设计语言：

- 页面容器使用 `MobileScreen` 或等价的安全区布局，内容最大宽度保持 `430`。
- 颜色只从 `useAppTheme()` 和 `app-theme.ts` 取值，使用现有 `background`、`surface`、`surfaceMuted`、`text`、`mutedText`、`line`、`primary`、`accent` 和 `success`。
- 浅色模式延续淡蓝背景、白色内容面；深色模式延续现有深灰背景和暖白文字。
- 间距遵循 `8/12/16/20/24/32`，主要面板圆角遵循现有 `16/24/32` 体系。
- 返回、二维码、复制、历史、确认、更多等操作使用现有 `MaterialCommunityIcons` 图标。
- 输入、分段控制、开关、底部弹层、按钮高度和阴影参考现有二维码工具页。
- 分数榜和提交列表使用分隔行，不堆叠卡片；卡片仅承载房间摘要、单个历史项和结算方案等有边界内容。
- 主按钮使用 `primary`，正向得分和已确认状态使用 `success`，负向得分和错误使用 `accent` 或现有错误色。
- 所有按钮保持稳定尺寸，最长昵称截断显示且可查看全名，分数使用等宽数字特性，避免实时变化造成布局跳动。
- 所有页面支持浅色、深色、390px 移动视口和桌面 Web，不出现文本、按钮或数字重叠。

### 5.3 关键交互细节

- 分数输入默认聚焦数字键盘，并提供 `+1`、`+5`、`-1`、`-5` 快捷步进。
- 提交前显示当前局合计差值；自己已提交后明确标识“已提交，可修改”。
- 确认阶段把“确认本局”作为唯一主按钮，同时显示 `已确认人数/总人数`。
- 网络断开时保留本机输入草稿，但不把草稿显示为已提交；重连后按最新 `roomVersion` 重新校验再提交。
- 房间进入后台或页面刷新后先拉取快照，再续订实时事件，避免只依赖 WebSocket 增量消息。
- 结束牌局、取消未确认局、移除玩家和发起冲正均需要明确二次确认。

## 6. 状态模型与业务不变量

### 6.1 房间状态

```text
WAITING -> ACTIVE -> SETTLED
   |          |
   +------> CANCELLED
```

- `WAITING`：等待玩家加入，可修改配置。
- `ACTIVE`：牌局进行中，配置锁定。
- `SETTLED`：已结算，只读。
- `CANCELLED`：房主在没有已确认局时取消，只读。

### 6.2 单局状态

```text
COLLECTING -> REVIEW -> CONFIRMED
     |          |
     +------> CANCELLED
```

- `COLLECTING`：收集每位玩家自己的分数。
- `REVIEW`：所有人已提交且总和为 0，等待全员确认。
- `CONFIRMED`：全员确认，分数已计入总榜，不可变更。
- `CANCELLED`：由房主取消，保留事件记录但不计分。

任何人在 `REVIEW` 阶段修改自己的分数都会撤销所有人的确认并回到 `COLLECTING`；重新满足零和后再次进入 `REVIEW`。

### 6.3 强制不变量

- 每位玩家起始累计分数为 `0`。
- 每局每位活跃参与者恰好有一条分数记录。
- 每局分数必须是 32 位有符号整数范围内的整数。
- 只有本局参与者本人可以写自己的分数。
- `CONFIRMED` 局的分数总和必须严格等于 `0`。
- 只有全体本局参与者都确认后才能进入 `CONFIRMED`。
- 累计分数只来自 `CONFIRMED` 局。
- 已确认记录不可原地更新或删除，只能通过关联冲正记录修正。
- 每分金额以整数分为单位存储，例如 `¥0.50` 存为 `50`，结算全程不使用浮点数。
- 所有参与者最终金额之和必须严格等于 `0`。

## 7. 技术方案

### 7.1 总体架构

沿用现有 Expo + Go + SQLite + WebSocket 架构，不引入新的运行时基础设施。

```text
Expo App / Web
  ├─ 房间页面与本地状态机
  ├─ REST 快照与命令
  ├─ WebSocket 增量事件
  └─ SecureStore / localStorage 临时身份
            |
            v
Go HTTP API
  ├─ Score Room Service
  ├─ Score Ledger Service
  ├─ Guest Token Service
  ├─ Settlement Engine
  └─ Existing Realtime Hub
            |
            v
SQLite
  ├─ 房间与参与者
  ├─ 逐局不可变账本
  ├─ 确认与事件序列
  └─ 结算快照
```

后端建议新增 `backend/internal/score/`，包含实体、存储、服务、结算算法和令牌校验；HTTP 适配器放在现有 `backend/internal/httpapi/`。前端建议新增 `frontend/features/tools/card-score/`，把页面、API、实时订阅、状态归并和展示组件分离，动态路由只负责装配。

### 7.2 数据模型

#### `score_rooms`

- `id`：UUID 主键。
- `code`：活跃房间内唯一的 6 位数字房间号。
- `host_user_id`：房主账号 ID。
- `name`：房间名称。
- `mode`：首版为 `generic`。
- `status`：房间状态。
- `max_players`：2 至 8。
- `cents_per_point`：每分金额，整数分。
- `version`：房间乐观并发版本号。
- `created_at`、`started_at`、`settled_at`、`expires_at`。

#### `score_participants`

- `id`：UUID 主键。
- `room_id`：房间 ID。
- `user_id`：注册用户 ID，可为空。
- `display_name`：房内昵称。
- `role`：`host` 或 `guest`。
- `status`：`active`、`removed` 或 `left`。
- `join_token_version`：临时令牌撤销版本。
- `joined_at`、`last_seen_at`。

#### `score_rounds`

- `id`：UUID 主键。
- `room_id`：房间 ID。
- `number`：普通局序号。
- `kind`：`normal` 或 `reversal`。
- `reverses_round_id`：冲正时关联原局。
- `status`：单局状态。
- `roster_json`：本局冻结参与者 ID 集合。
- `created_by`、`created_at`、`confirmed_at`、`cancelled_at`。

#### `score_entries`

- `round_id`、`participant_id`：联合唯一。
- `delta_points`：本局增减分。
- `revision`：分数每次修改后递增，用于确认绑定。
- `submitted_at`、`updated_at`。

#### `score_confirmations`

- `round_id`、`participant_id`：联合唯一。
- `entry_revision`：确认时的分数修订版本。
- `confirmed_at`。

#### `score_room_events`

- `room_id`、`sequence`：房内严格递增事件序列。
- `event_type`、`payload_json`、`actor_participant_id`、`created_at`。

#### `score_command_receipts`

- `actor_participant_id`、`client_action_id`：联合唯一幂等键。
- `command_type`、`request_hash`：防止同一幂等键被不同请求复用。
- `result_room_version`、`result_json`、`created_at`：保存首次成功结果。

#### `score_settlements`

- `room_id`：唯一。
- `room_version`：结算使用的房间版本。
- `balances_json`：最终分数与金额快照。
- `transfers_json`：最少转账方案。
- `created_at`。

所有涉及提交分数、确认单局、冲正和结算的操作必须在 SQLite 事务中完成，并在同一事务内写入命令回执、更新 `room.version` 与追加事件，避免“数据已写入但事件未生成”。

### 7.3 HTTP 接口

建议使用现有 `/api/v1` 命名空间：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/score-rooms` | 登录用户创建房间 |
| `POST` | `/score-rooms/join` | 使用房间号或邀请令牌加入 |
| `GET` | `/score-rooms/{roomId}` | 获取完整房间快照 |
| `POST` | `/score-rooms/{roomId}/start` | 房主开始牌局 |
| `POST` | `/score-rooms/{roomId}/rounds` | 房主发起新一局或冲正局 |
| `PUT` | `/score-rounds/{roundId}/entries/me` | 提交或修改自己的分数 |
| `POST` | `/score-rounds/{roundId}/confirm` | 确认当前分数修订 |
| `POST` | `/score-rounds/{roundId}/cancel` | 房主取消未确认局 |
| `POST` | `/score-rooms/{roomId}/settle` | 房主结束并结算 |
| `GET` | `/score-rooms/history` | 房主查看历史房间 |

写接口统一接收：

- `clientActionId`：UUID，用于网络重试幂等。
- `expectedRoomVersion`：客户端最后看到的版本。

服务端先查幂等回执，再检查版本：同一参与者重复提交同一 `clientActionId` 时返回第一次成功结果；同一键对应不同请求体时返回 `409`。非重复请求版本不一致时返回 `409` 和最新房间快照摘要，客户端归并后提示用户重试。

### 7.4 实时同步

复用现有 Realtime Hub 和 WebSocket ticket 机制。登录用户沿用账号令牌；临时玩家使用房间级 guest token 换取只允许订阅指定房间的 realtime ticket。

核心事件：

- `score.participant.joined`
- `score.participant.updated`
- `score.room.started`
- `score.round.started`
- `score.entry.submitted`
- `score.round.review_ready`
- `score.round.confirmation_updated`
- `score.round.confirmed`
- `score.round.cancelled`
- `score.room.settled`

事件携带 `roomId`、`roomVersion` 和 `sequence`。客户端发现序号跳跃、版本倒退或重连时，停止应用增量并重新拉取快照。WebSocket 仅用于通知和低延迟同步，服务端数据库快照始终是事实来源。

### 7.5 临时身份与安全

- guest token 使用服务端签名，包含 `roomId`、`participantId`、`tokenVersion` 和过期时间。
- 临时令牌只能调用本房间且属于自己的写接口。
- 二维码邀请令牌与房间生命周期绑定，房间结束后立即失效。
- 房间号加入、昵称尝试和令牌换票均使用现有限流能力，降低枚举和骚扰风险。
- 服务端从令牌身份解析参与者，不接受客户端传入的任意 `participantId` 作为写入主体。
- 房间结束后 guest token 转为只读并在 24 小时后失效；房主历史按产品数据保留策略保存。
- 日志不得记录完整 guest token、邀请令牌或用户输入的备注内容。

### 7.6 最少转账算法

玩家最终余额为：

```text
balance_cents = total_points * cents_per_point
```

正数为应收，负数为应付。由于最多 8 人，结算引擎使用带剪枝和记忆化的深度优先搜索，在所有合法债权债务抵消方案中寻找交易笔数最少的方案，而不是使用只能保证“较少笔数”的普通贪心算法。

确定性规则：

1. 先过滤余额为 0 的玩家。
2. 搜索目标优先最少交易笔数。
3. 笔数相同时，按参与者加入顺序和稳定 ID 排序，确保相同输入总是生成相同结果。
4. 输出前再次校验每位玩家的转入减转出等于其最终余额，且所有转账金额均为正整数分。

人数上限为 8，经过符号配对、相同余额去重、完全抵消优先和余额状态记忆化后，精确搜索的状态空间可控。算法不以普通贪心结果冒充最优解；进入搜索前先拒绝人数、金额范围或总和不合法的输入。

## 8. 异常与边界处理

- 玩家断线：显示离线状态并允许原身份重连；待确认局不自动越过该玩家。
- 重复提交：由 `clientActionId` 幂等处理，不重复追加分数。
- 两台设备同时使用同一 guest token：后一次写入按版本冲突处理，实时显示最新状态。
- 玩家中途离开：只能在两局之间移除；历史得分和最终结算保留。
- 房主离线：房间保持当前状态，房主重连后继续；首版不自动转让房主。
- 房间满员或已结束：加入接口返回明确状态和可恢复操作。
- 分数和不为 0：禁止进入确认，并显示精确差值。
- 分数极值：前端提前限制，后端仍做整数范围校验。
- 待确认局结束牌局：禁止结算，房主需先完成或取消该局。
- 结算请求重试：如果房间已结算，直接返回同一结算快照。
- 服务端重启：从 SQLite 快照和事件序列恢复，不依赖内存房间状态。

## 9. 测试策略

### 9.1 后端测试

- 房主与 guest token 的权限边界。
- 创建、加入、开始、提交、修改、确认、取消和结算状态机。
- 零和校验、全员确认、确认撤销和已确认不可变。
- 幂等重试和 `expectedRoomVersion` 冲突。
- 断线重连后的快照与事件序列恢复。
- 冲正局完整审计链。
- 整数金额换算和金额总和不变量。
- 对 2 至 8 人的已知案例与枚举案例验证精确最少转账笔数。
- SQLite 事务失败时不产生半写入数据或孤立事件。

### 9.2 前端测试

- 房间快照归并、增量事件应用和 sequence 缺口恢复。
- 分数输入、快捷步进、正负号、边界值和草稿保留。
- 各状态下主按钮、禁用条件、确认人数和差值提示。
- 刷新后 guest 身份恢复以及过期令牌降级。
- 浅色、深色和长昵称下的布局稳定性。

### 9.3 内部浏览器验收

按用户要求，功能完成后使用 Codex 内部浏览器进行实际验收，不以静态截图替代交互测试：

1. 在多个浏览器标签页模拟 1 名房主和 3 名临时玩家。
2. 完成创建房间、扫码/链接加入、开始牌局和至少 3 局记分。
3. 覆盖一次非零和错误、一次修改后重新确认、一次刷新重连和一次冲正。
4. 验证所有标签页的累计分数、确认状态和结算结果一致。
5. 在桌面 `1280x720`、移动 `390x844` 以及浅色/深色模式检查文字、按钮、数字和弹层无重叠、无横向溢出。
6. 检查控制台错误、失败网络请求、WebSocket 重连和快照恢复。

## 10. 验收标准

- 登录用户可在 30 秒内创建房间并展示可用邀请二维码/房间号。
- 未注册玩家可在 15 秒内通过临时昵称加入，不需要创建账号。
- 每位玩家只能修改自己的当前局分数。
- 本局总和不为 0 时，任何人都无法确认入账。
- 总和为 0 且全员确认后，所有在线客户端在 1 秒内看到一致累计结果。
- 刷新或短暂断线后不会丢失身份、重复玩家或重复记分。
- 已确认局无法直接修改；冲正后历史和总分均可追溯。
- 结束牌局后生成金额守恒且交易笔数最少的转账方案。
- 功能在现有 Funbox 浅色、深色、App 和 Web 风格下保持一致。
- 内部浏览器的桌面与移动验收无阻断级控制台错误、网络错误或布局溢出。

## 11. 推荐实施顺序

1. 后端数据模型、账本不变量和精确结算算法。
2. 创建/加入/快照/逐局命令接口和 guest token。
3. Realtime Hub 房间事件与断线恢复。
4. 前端工具入口、房间状态层和创建/加入流程。
5. 记分页、确认流程、历史与冲正。
6. 结算页和最少转账展示。
7. 自动化测试、内部浏览器多标签页验收和视觉收尾。

该顺序优先固定不可变账本和权限边界，再接入实时 UI，减少后期因状态模型变化造成的返工。
