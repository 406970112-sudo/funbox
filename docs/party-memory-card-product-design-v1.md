# FunBox 聚会记忆卡 产品设计方案 V1

> 版本：V1 完整一期
> 日期：2026-08-06
> 状态：待评审
> 定位：把一场真实聚会的参与者、餐厅、账单、照片、菜品评价、请客关系和下次意愿收进同一张记忆卡，并在下次聚餐前直接引用最近一次真实记录做准备。

## 1. 产品概述

### 1.1 一句话定位

“聚会记忆卡”是一个以真实聚会记录为中心的轻量工具：用户记录一次真实聚餐后，自动形成一张包含记账、相册、社交记忆和下次准备的卡片；下次准备聚餐时，不再靠聊天记录和账单截图拼记忆。

### 1.2 解决的问题

| 场景 | 现状 | 问题 |
| --- | --- | --- |
| 聚会结束后 | 账单在付款记录，照片在相册，评价在聊天里 | 信息分散，后续想找很麻烦 |
| 下次聚餐 | 只记得“上次王明请客”，但忘了谁参加、花了多少 | 缺少可追溯的真实记录 |
| 餐厅选择 | 记得烤鱼不错，但忘了停车不好停 | 评价和真实经验没有沉淀 |
| 菜品决策 | 上次点的菜好不好吃，每个人想法不同 | 没有真实的菜品口碑记录 |
| 社交记忆 | 照片只保存在个人相册 | 参与人没有共同补充和回看的入口 |

### 1.3 与 FunBox 现有能力的衔接

- 复用账号、JWT、SQLite、统一工具注册、主题系统、好友关系、消息中心与 WebSocket 实时通知。
- 参与人可从当前账号的真实好友中选择，也可手动输入真实姓名或昵称。
- 照片存储复用现有私有存储目录与图片压缩能力，不引入第三方图床。
- 工具入口沿用 `backend/internal/access/feature_registry.json` 注册方式，工具列表、最近使用、首页推荐位自动生效。
- 消息中心用于好友协作通知，例如“被邀请参与记录”“有人上传了照片”“有人给菜品点了好评”。

### 1.4 一期全量边界

本方案不设分期，以下能力在同一个版本一次交付：

- 记忆卡的创建、编辑、删除、归档与查看。
- 参与者管理：真实好友邀请、手动输入参与人、邀请状态、退出协作。
- 账单记录：总费用、请客方式、请客参与人、费用可见性、真实人均计算。
- 相册：真实拍照或相册上传、封面设置、照片删除。
- 菜品：真实菜名、可选价格、真实参与人评价与投票。
- 餐厅印象：停车、口味、环境、服务、位置等真实文字记录。
- 下次意愿：参与人真实投票“想去 / 一般 / 不想去”。
- 下次聚餐准备页：引用最近一次真实卡片，展示请客轮换、餐厅事实、热门菜品、人均与投票。
- 搜索、筛选、导出备份、空态、错误态、权限校验与前后端测试。

## 2. 真实数据原则（硬性要求）

1. 首次进入“聚会记忆卡”为空态，不预置任何聚会、餐厅、参与人、照片、账单、菜品或评价。
2. 餐厅名称、地址、参与人姓名、菜名、印象文本只能来自用户真实录入。
3. 参与者只能来自当前账号真实好友，或用户手动输入的真实姓名/昵称，不允许内置示例人物。
4. 账单金额由用户填写，人均由服务端基于真实参与人数计算；未填写时显示“暂无账单”。
5. 照片只能来自真实拍照或相册上传，不允许内置示例图片。
6. “下次还去”只能来自参与人真实投票；没有投票时显示“暂无投票”。
7. “上次王明请客”“烤鱼评价不错”“停车不方便”等下次准备内容，只能引用最近一次真实卡片中的真实字段，不允许 AI 推断或补全。
8. 菜品排序只按真实好评数和真实时间排序，不做推荐算法。
9. 设计稿中出现的示例餐厅、参与人、金额、照片与评价仅用于表达“录入后界面”的版式，正式产品首次进入为空，运行时不会写入数据库。

## 3. 产品目标与设计原则

### 3.1 产品目标

1. 用户 60 秒内完成一次“创建记忆卡 + 必填信息”的基础记录。
2. 每张卡都能说清“有哪些人、在哪吃、花了多少、拍了什么、谁请客、点了什么、下次还想不想去”。
3. 下次聚餐前，用户能在 10 秒内看到最近一次真实聚会的请客、停车、菜品、人均和投票。
4. 产品运行期间没有任何 mock 数据、种子数据或 AI 编造内容。

### 3.2 设计原则

- 真实优先：所有数字、名称、照片、评价和时间都来自真实操作。
- 缺字段不补造：没有照片显示“暂无照片”，没有账单显示“暂无账单”，没有投票显示“暂无投票”。
- 一卡聚合：记账、相册、社交记忆和下次准备统一在记忆卡内，不做多个分散入口。
- 轻量协作：只有真实参与人可以共同补充，不做公开分享、排行榜或陌生人社交。
- 一期全量：搜索、协作、导出、权限和状态全部在本版本完成，不拆二期。

## 4. 目标用户与场景

| 用户 | 核心场景 | 产品应满足 |
| --- | --- | --- |
| 经常聚餐的朋友 | 每两周一次老友聚餐 | 快速记录一次聚会，下次直接看上次请客和餐厅印象 |
| 聚会发起人 | 需要确定下次去哪、谁请客 | 从最近一次真实卡片获得请客轮换、停车和菜品参考 |
| 朋友圈相册负责人 | 每次聚会拍很多照片 | 把真实照片按聚会归档，参与人共同上传 |
| 喜欢记账的用户 | 想知道每次聚会人均花多少 | 记录总费用和请客方式，服务端按真实人数计算人均 |
| 对餐厅有要求的用户 | 想记住哪家店好吃、哪家停车难 | 记录停车、口味、环境、服务等真实印象 |
| 想回顾社交记忆的用户 | 翻看一年前的聚会 | 按餐厅、参与人、菜名、时间搜索真实记忆卡 |

## 5. 产品结构

### 5.1 入口

- 工具注册名：`party-memory-card`
- 工具名称：聚会记忆卡
- 分类：生活
- 路由：`/tools/party-memory-card`
- 入口图标：`party-popper`，备用 `account-group-outline`
- 状态：一期发布时注册为 `available`
- 权限：`normal / vip / svip / admin` 均可使用，V1 不做会员权益差异
- 搜索关键词：聚会、聚餐、记忆卡、请客、谁请客、聚餐记录、餐厅评价、停车、烤鱼、账单、AA、下次聚餐、照片、相册、老友聚餐

### 5.2 页面清单

| 页面 | 说明 |
| --- | --- |
| 首页 | 记忆卡列表、真实统计、搜索、筛选、快速记录入口 |
| 创建记忆卡 | 基本信息、照片账单、印象评价三组表单 |
| 记忆卡详情 | 封面、参与人、相册、菜品、账单、印象、下次意愿、协作动态 |
| 协作记录 | 参与人邀请状态、共同上传照片、菜品投票、印象补充 |
| 下次聚餐准备 | 最近一次真实卡片摘要、请客轮换、餐厅事实、菜品好评、人均、投票 |
| 历史卡片 | 搜索、筛选、排序、导出备份 |

### 5.3 核心流程

```text
进入聚会记忆卡
  -> 首页：搜索 / 记忆卡列表 / 快速记录
  -> 创建记忆卡：日期 + 餐厅 + 参与人 + 谁请客（必填）
  -> 补充内容：真实照片 + 菜品评价 + 账单 + 停车/环境印象 + 下次意愿
  -> 保存记忆卡：写入真实数据库
  -> 分享给真实好友：好友接受后共同补充
  -> 下次聚餐：查看最近一次真实卡片，发起新聚会
```

## 6. 功能设计

### 6.1 首页 / 记忆卡列表

- 顶部搜索框覆盖餐厅名称、地址、参与人姓名、菜名、聚会主题、印象文本。
- 统计区展示真实总数：聚会次数、照片数量、累计消费；首次进入全部为 0。
- 列表按 `party_date` 倒序展示真实记忆卡，每张卡显示日期、餐厅、参与人快照、请客方式和是否有照片。
- 支持筛选：请客方式（全部 / 请客 / AA）、是否想去（想去 / 一般 / 不想去）、是否有照片。
- 首次进入为空态：只展示搜索框、0 统计、真实空态说明和“拍照记录 / 手动记录”入口，不预置示例卡。
- 删除卡片需要二次确认；删除后不生成虚假历史。

### 6.2 创建记忆卡

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| 聚会日期 | 是 | 默认真实当前时间，可修改，格式为本地日期时间 |
| 聚会主题 | 否 | 单行文本，最长 40 字，例如“8月老友聚餐” |
| 餐厅 / 地点 | 是 | 单行文本，最长 60 字，必须是用户真实录入 |
| 地址 | 否 | 单行文本，最长 120 字 |
| 参与人 | 是 | 2-50 人，可从真实好友选择或手动输入 |
| 谁请客 | 是 | 从参与人中选择，或选择“AA 分摊” |
| 总费用 | 否 | 非负数字，单位元，支持小数点后两位 |
| 费用可见性 | 否 | 创建人 / 参与人可见，默认参与人可见 |

- 保存时校验必填项；缺失字段返回明确错误并保留已填内容。
- 参与人少于 2 人时提示“至少需要 2 位真实参与人”。
- 保存成功后进入记忆卡详情，可继续补充照片、菜品和印象。

### 6.3 参与人管理

- 参与人类型：
  - `friend`：从当前账号真实好友中选择，可发送协作邀请。
  - `manual`：用户手动输入真实姓名/昵称，不进入协作，只作为卡片成员展示。
- 邀请状态：`pending / joined / declined`。
- 好友收到消息中心通知后，可打开卡片并选择“参与记录”。
- 已加入的好友可以上传照片、评价菜品、补充印象、投票“下次还去”。
- 创建人可移除参与人；移除后该参与人已有的照片、评价和投票保留真实历史，但不再显示为当前成员。
- 创建人可退出共享关系，但不影响已产生的真实记录。

### 6.4 餐厅与下次意愿

- 餐厅名称和地址必须真实录入。
- 餐厅印象支持维度：停车、口味、环境、服务、位置、其他。
- 每个印象必须包含真实文字内容，最长 100 字，可由创建人或已加入好友补充。
- 同一维度可有多条真实印象，下次准备页按“最近一条 + 记录人数”展示。
- “下次还去”投票：
  - 选项：想去 / 一般 / 不想去。
  - 每个参与人只能投一次，重复投票更新原投票。
  - 没有投票时显示“暂无投票”。

### 6.5 账单与请客

- 总费用为可选字段；填写后服务端保存为分单位整数，展示时格式化。
- 请客方式：
  - `member`：指定一位真实参与人请客。
  - `aa`：AA 分摊。
  - `other`：非参与人垫付，备注最长 40 字。
- 人均计算：`member / other` 模式下不计算人均；`aa` 模式下由服务端按真实参与人数计算。
- 费用可见性为 `owner` 时，仅创建人可见金额；`participants` 时已加入好友可见。
- 不接入支付平台，不自动读取支付账单，不做自动分账。

### 6.6 照片与相册

- 照片只能来自真实拍照或相册上传，单卡最多 30 张。
- 上传后生成私有文件地址和缩略图，支持设置封面。
- 参与人可删除自己上传的照片；创建人可删除整卡照片。
- 照片不参与 AI 识别、不自动生成标题、不自动打标签。
- 记忆卡详情中的“照片”区按真实上传时间倒序展示，封面固定在首位。

### 6.7 菜品与真实评价

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| 菜名 | 是 | 单行文本，最长 40 字，真实菜名 |
| 价格 | 否 | 非负数字，单位元，保存为分 |
| 评价 | 是 | 好吃 / 一般 / 不推荐 |
| 评价人 | 是 | 当前真实参与人 |

- 每个参与人对同一道菜只能投一次，重复投票更新原投票。
- 菜品列表按真实好评数降序，其次按创建时间升序，不做算法推荐。
- 有评价时展示“N 人觉得好吃 / 一般 / 不推荐”；没有评价时展示“暂无评价”。

### 6.8 协作与动态

- 共享卡片产生真实动态事件，例如：
  - 王明 确认总费用 486 元
  - 李雷 上传了 2 张照片
  - 韩梅梅 给烤鱼点了好评
  - 韩梅梅 补充了“停车不方便”
- 动态只记录真实操作，不允许手动伪造或补写。
- 动态按真实发生时间倒序展示，删除对应数据时动态保留但标注“内容已删除”。
- 好友协作通过消息中心通知，不在卡片外生成公开信息。

### 6.9 下次聚餐准备页

- 只引用当前用户有权限查看的、按 `party_date` 倒序的最新一张真实卡片。
- 如果没有任何真实卡片，显示空态“还没有真实记录，先记录一次聚会”。
- 请客轮换：
  - 最近一次为 `member` 时显示“上次由 X 请客”，并提供“选择本次请客”入口。
  - 最近一次为 `aa` 时显示“上次 AA 分摊”。
  - 不自动指定本次请客人，用户从真实参与人中选择。
- 餐厅事实：
  - 停车、口味、环境、服务、位置等印象只引用真实记录。
  - 无印象时显示“暂无真实印象”。
- 菜品参考：
  - 展示最近一次卡中真实好评最多的菜品，最多 5 道。
  - 无菜品或无人评价时显示“暂无菜品评价”。
- 人均与费用：
  - 只有当前用户有费用查看权限时才展示人均。
  - 无权限或未填写时显示“暂无账单”。
- 投票：
  - 展示最近一次卡中真实“想去 / 一般 / 不想去”人数。

### 6.10 搜索、筛选与导出

- 搜索范围：餐厅名称、地址、参与人姓名、菜名、聚会主题、印象文本。
- 排序：最近一次、最早一次、消费最高、照片最多。
- 无结果时显示“没有找到符合条件的真实记忆卡”，保留搜索词并提供清空筛选。
- 导出格式：JSON / CSV，仅包含当前用户有权限查看的真实数据。
- 导出文件不包含其他用户私有账单；费用可见性为 `owner` 时导出中不包含金额。

### 6.11 真实数据机制

| 数据 | 来源 | 校验要求 |
| --- | --- | --- |
| 餐厅名称 | 用户真实录入 | 非空、长度校验、去首尾空格 |
| 参与人 | 真实好友或手动输入 | 非空、去重、2-50 人 |
| 账单金额 | 用户真实录入 | 非负数字，服务端保存为分 |
| 照片 | 拍照或相册上传 | 校验文件类型、大小，存私有文件 |
| 菜品评价 | 参与人真实投票 | 一人一菜一票，更新不重复计票 |
| 餐厅印象 | 用户真实文字录入 | 维度必填、内容非空 |
| 下次意愿 | 参与人真实投票 | 一人一卡一票 |
| 动态 | 服务端真实操作事件 | 不允许客户端伪造 |

禁止事项：
- 不生成任何种子聚会、种子餐厅、示例参与人或演示照片。
- 不由 AI 推断餐厅评价、停车情况、推荐菜或下次意愿。
- 不在没有真实数据时展示“已验证”“推荐”“大多数人都说好”等断言。
- 不在 API 或存储层返回虚假计数。

## 7. 数据模型

```text
party_cards
  id, owner_user_id, title, party_date, venue_name, venue_address,
  host_type, host_participant_id, total_amount_cents,
  expense_visibility, card_status, share_mode,
  archived_at, created_at, updated_at

party_participants
  id, card_id, user_id nullable, name, kind,
  invite_status, can_edit, sort_order, created_at, updated_at

party_photos
  id, card_id, user_id, file_url, thumb_url,
  kind, taken_at, sort_order, created_at

party_dishes
  id, card_id, created_by_user_id, name,
  price_cents nullable, sort_order, created_at

party_dish_votes
  id, dish_id, participant_id, rating,
  created_at, updated_at
  unique(dish_id, participant_id)

party_venue_notes
  id, card_id, participant_id, dimension,
  content, created_at

party_again_votes
  id, card_id, participant_id, vote,
  created_at, updated_at
  unique(card_id, participant_id)

party_activity_events
  id, card_id, user_id, action,
  payload_json, created_at
```

时间规则：
- API 使用 ISO 8601 或 `YYYY-MM-DD HH:mm:ss`，客户端按用户本地时区展示。
- 聚会日期由用户选择或默认真实当前时间，服务端不伪造当前时间。
- “最近一次”按真实 `party_date` 倒序，不使用创建时间代替。

## 8. 接口设计

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/party-memory-card/summary` | 首页统计与最近卡片 |
| GET | `/api/v1/party-memory-card/cards?q=&filter=&sort=` | 卡片列表与搜索 |
| POST | `/api/v1/party-memory-card/cards` | 创建记忆卡 |
| GET | `/api/v1/party-memory-card/cards/{id}` | 记忆卡详情 |
| PATCH | `/api/v1/party-memory-card/cards/{id}` | 编辑记忆卡 |
| DELETE | `/api/v1/party-memory-card/cards/{id}` | 删除或归档 |
| POST | `/api/v1/party-memory-card/cards/{id}/participants` | 添加参与人 |
| PATCH | `/api/v1/party-memory-card/cards/{id}/participants/{pid}` | 更新邀请状态或权限 |
| DELETE | `/api/v1/party-memory-card/cards/{id}/participants/{pid}` | 移除参与人 |
| POST | `/api/v1/party-memory-card/cards/{id}/photos` | 上传真实照片 |
| DELETE | `/api/v1/party-memory-card/cards/{id}/photos/{photoId}` | 删除照片 |

| GET | `/api/v1/party-memory-card/export?format=json\|csv` | 导出当前用户真实数据 |

说明：
- 所有接口要求登录，沿用 JWT 鉴权与限流中间件。
- 新增模块放在 `backend/internal/partymemorycard/`，在现有 `httpapi` 注册路由。
- 响应中的缺失字段返回 `null`，不补造空字符串或“暂无”以外的文案。
- 动态事件由服务端在真实写入时生成，接口不接受伪造事件。

## 9. 页面与交互设计

- 沿用 FunBox 视觉体系：浅蓝画布、白色表面、深藏青重点、品牌蓝主色。
- 本工具补充语义色：请客珊瑚 `#ff6b8f`、好评绿 `#1db991`、停车/印象琥珀 `#f1a33b`。
- 内容区最大 430px 移动宽度，宽屏居中。
- 搜索框、照片上传、参与人选择、菜品评价、投票、动态使用稳定尺寸控件，点击区域不小于 44px。
- 图标沿用 Material Community Icons / lucide 对应图标。
- 支持浅色与深色主题；320px、390px、430px 视口下文字不溢出、元素不重叠。
- 不做教程式大段说明，空态只给可执行动作。

## 10. 状态与异常处理

| 场景 | 处理 |
| --- | --- |
| 首次进入，无卡片 | 真实空态 + 0 统计 + 记录入口，不预置数据 |
| 参与人少于 2 人 | 保存按钮禁用并提示至少 2 人 |
| 照片上传失败 | 保留表单内容，提示重试 |
| 金额格式错误 | 保留输入，提示格式要求 |
| 无照片 / 无账单 / 无投票 | 显示“暂无照片 / 暂无账单 / 暂无投票” |
| 好友未接受邀请 | 显示“待接受”，不阻塞创建人记录 |
| 费用无权限 | 显示“暂无账单”，不返回金额 |
| 删除卡片 | 二次确认；共享成员删除自己的照片、评价时保留真实历史 |
| 同步失败 | 展示已缓存真实数据并标注更新时间，不展示 mock |
| 导出失败 | 保留页面状态，提示重试 |

## 11. 一期交付清单

本方案不设分期，以下内容在同一版本一次交付：

- 记忆卡 CRUD、必填校验、归档与删除。
- 参与人管理、真实好友邀请、手动输入、邀请状态。
- 账单、请客方式、费用可见性、服务端人均计算。
- 照片上传、封面设置、删除、缩略图。
- 菜品添加、编辑、删除、真实评价与投票。
- 餐厅印象、下次意愿投票。
- 共享卡片、协作动态、消息中心通知。
- 下次聚餐准备页、请客轮换入口、真实餐厅事实、菜品好评、投票。
- 搜索、筛选、排序、导出备份。
- 空态、加载、错误、同步失败状态。
- 浅色 / 深色主题与 320 / 390 / 430 响应式。
- 单元测试覆盖校验、计票、人均、权限、搜索、导出与下次准备逻辑。

## 12. 明确不做

- 不做 AI 菜品识别、AI 餐厅评价、AI 自动总结或推荐算法。
- 不做支付平台接入、支付账单自动同步或自动分账。
- 不做公开分享、公开相册、排行榜或陌生人社交。
- 不做商家数据库、地图 POI 自动补全或餐厅点评聚合。
- 不做种子数据、演示数据、mock 数据或示例记忆卡。
- 不做会员权益差异，V1 所有角色可用。

## 13. 风险与开放问题

| 问题 | 当前建议 | 影响 |
| --- | --- | --- |
| 用户不愿完整填写 | 只保留日期、餐厅、参与人、请客必填 | 保证记忆卡可用，其余可后续补充 |
| 照片存储占用 | 复用私有存储目录，单卡最多 30 张 | 需要评估存储配额 |
| 好友不参与协作 | 不阻塞创建，待接受状态保留 | 卡片仍是创建人的真实记录 |
| 账单隐私 | 增加费用可见性控制 | 参与人可见时需二次确认 |
| “下次想去”人数可信度 | 一人一卡一票，重复投票更新 | 避免重复计数 |
| 下次准备引用唯一性 | 只取最近一张真实卡片 | 不跨卡混算，避免误导 |

## 14. 验收清单

- 首次进入没有任何预置聚会、餐厅、参与人、照片、账单或评价。
- 创建记忆卡后，首页、列表、详情、统计数字全部一致。
- 支持真实好友选择和手动输入参与人，参与人数 2-50。
- 支持真实照片上传、封面设置和删除。
- 支持菜品添加、编辑、删除和真实评价投票，一人一菜一票。
- 支持停车、口味、环境、服务、位置等真实印象。
- 支持“想去 / 一般 / 不想去”投票，无投票时显示“暂无投票”。
- 下次准备页只引用最近一次真实卡片，请客、停车、菜品、人均、投票均来自真实字段。
- 费用可见性控制生效，无权限时不返回金额。
- 搜索可命中餐厅、参与人、菜名、主题和印象文本。
- 导出文件只包含当前用户有权限的真实数据。
- 320px、390px、430px 视口无文字溢出和元素重叠。
- 浅色 / 深色主题均可读。
- 接口全部带 JWT 鉴权，未登录返回 401。
