# FunBox 今日运气签 产品设计方案 V1

> 版本：V1 完整一期
> 日期：2026-08-06
> 状态：待评审
> 定位：一张由真实天气、空气质量、农历和节假日数据生成的“轻娱乐每日签”。它不预测吉凶，不产出占卜结论，只把今天真实存在的数据翻译成可执行的小灵感。

## 1. 背景与问题

很多人喜欢在每天开始前有一个轻量的“今日仪式”，但市面上常见的运势、抽签和星座内容普遍存在三个问题：

| 现状 | 问题 |
| --- | --- |
| 随机抽一句“今日运势” | 结果不可解释，用户无法判断依据 |
| 大量使用预置文案和占位数据 | 缺少真实来源，容易显得廉价或不可信 |
| 把“宜忌”包装成行为指导 | 容易滑向封建迷信或健康误导 |

FunBox 已经有账号、JWT、SQLite、工具注册、主题系统和“真实数据优先”的产品原则，新增“今日运气签”可以复用同一套基础设施，不需要引入新服务。

## 2. 对原始想法的补充

原始想法是：今日幸运颜色、今日适合做的小事、今日挑战、今日鼓励。

在此基础上补充十点：

1. 定位为“轻娱乐每日签”，不叫运势预测，不做吉凶、宜忌、命理或星座结论。
2. 所有内容由真实数据驱动，同一个地点同一天结果确定，不使用随机数生成签文。
3. 每个字段带 `source`、`fetchedAt`、`license`，可追溯到具体数据源。
4. “今日幸运颜色”改为“今日灵感色”，由天气、空气质量和季节共同决定，并展示依据。
5. “适合做的小事”由真实天气、AQI、紫外线、降雨概率、节假日和节气触发，每条附 `ruleId` 和理由。
6. “今日挑战”同样来自规则引擎，不做随机任务，不鼓励危险或健康敏感行为。
7. “今日鼓励”使用当天真实数据写成，例如“AQI 37 优，适合开窗透气”，不生成无来源的心灵鸡汤。
8. 数据源失败时不补造字段，只展示已经获取到的真实字段，并明确标记为“部分可用”。
9. 首次使用没有默认城市、默认签文或默认完成记录，所有内容都来自用户真实选择和真实数据。
10. 本方案所有功能在一个版本内一次做完，不设二期、不设分期上线的功能项。

## 3. 产品目标与设计原则

### 3.1 产品目标

1. 用户 10 秒内看懂今天的“小灵感”，30 秒内完成一次挑战打卡。
2. 页面上的每一个数据字段都能追到来源、抓取时间和许可。
3. 数据源异常时页面仍然真实可用，但绝不补造缺失内容。
4. 产品运行期间没有任何 mock 数据、种子数据或 AI 编造的签文。

### 3.2 设计原则

- 真实优先：字段缺则隐藏，不为了填满页面而编造。
- 可解释：每条建议都展示触发它的真实理由。
- 确定性：同一位置同一天返回同一张签。
- 轻娱乐：只提供灵感与鼓励，不提供命运结论。
- 一期全量：核心页面、规则、接口、状态和测试一次交付。
- 隐私克制：不保存精确坐标，不生成个人命理画像。

## 4. 目标用户与场景

| 用户 | 核心场景 | 产品应满足 |
| --- | --- | --- |
| 通勤上班族 | 早晨打开手机想获得一点今日灵感 | 10 秒看到天气、AQI 和一件可做的小事 |
| 喜欢仪式感的年轻人 | 想要每天有“抽一张签”的乐趣，但拒绝迷信 | 一张可解释、有真实依据的轻娱乐签 |
| 关注天气与空气的用户 | 想知道今天适合散步、开窗还是防晒 | 建议直接关联真实温度、降雨、UV 和 AQI |
| 想要小改变的用户 | 晚上复盘今天完成了一件小事 | 挑战打卡只记录用户真实完成动作 |
| 数据敏感用户 | 担心功能使用假数据 | 每个字段都能点开查看来源和抓取时间 |

## 5. 产品结构

### 5.1 入口

- 工具注册名：`daily-luck-sign`
- 工具名称：今日运气签
- 分类：生活
- 路由：`/tools/daily-luck-sign`
- 入口图标建议：`palette-outline`（Material Community Icons）
- 状态：一期发布时直接注册为 `available`
- 权限：`normal / vip / svip / admin` 均可使用，V1 不做会员权益差异
- 推荐注册字段：

```text
id: "daily-luck-sign"
name: "今日运气签"
tagline: "真实数据的每日轻娱乐签"
description: "由天气、空气质量、农历和节假日生成今日灵感色、小事、挑战与鼓励，字段级可溯源，不预测吉凶。"
category: "生活"
badges: ["真实数据", "不测吉凶", "每日更新"]
keywords: ["今日", "运气签", "幸运色", "每日签", "今日挑战", "今日小事", "天气签"]
usageLabel: "查看今日签"
accentColor: "#2f9b8f"
```

### 5.2 页面清单

| 页面 | 说明 |
| --- | --- |
| 今日签首页 | 日期、位置、灵感色、天气摘要、小事、挑战、鼓励 |
| 行动与挑战 | 三类建议的分组展示，每条带理由和来源 |
| 真实数据明细 | 天气、空气、农历、节假日、位置的字段级来源 |
| 我的完成 | 用户真实完成的挑战记录与统计 |
| 位置与数据源 | 城市选择、定位权限、数据源健康状态 |
| 部分可用降级 | 数据源失败时展示已有真实字段，缺字段不补造 |

以上页面均为一期交付范围。

### 5.3 核心流程

```text
进入今日运气签
  -> 确认位置：手动选择城市或系统定位
  -> 后端按日期 + 位置拉取真实数据
  -> 规则引擎生成：灵感色 / 小事 / 挑战 / 鼓励
  -> 首页展示，每条建议可查看理由与来源
  -> 用户完成挑战后写入“我的完成”
  -> 次日自动刷新；数据失败时进入“部分可用降级”
```

## 6. 功能设计

### 6.1 今日签首页

- 顶部显示本地日期、周几、农历日期和位置名称。
- 状态胶囊展示“完整可用 / 部分可用 / 数据获取中”。
- 主卡片为“今日灵感色”，展示色值、颜色名称和生成依据，例如“AQI 37 优 + 毛毛雨 -> 雨雾青”。
- 天气摘要展示今日最高/最低温、降雨概率、UV、AQI，全部来自真实字段。
- 下方按“适合做的小事”“今日挑战”“今日鼓励”三个区块展示建议。
- 右上角提供“查看数据明细”和“保存签图”。

### 6.2 行动与挑战

- “适合做的小事”最多展示 3 条，每条包含标题、理由、来源标签。
- “今日挑战”最多展示 2 条，每条提供“完成打卡”按钮。
- “今日鼓励”最多展示 2 条，内容必须包含至少一个真实数据值。
- 每条建议带 `ruleId`，点击后展开触发条件和原始数据。
- 完成打卡后按钮变为“已完成”，写入真实完成记录。

### 6.3 真实数据明细

- 按数据源分组：天气、空气质量、农历/节气、节假日、位置。
- 每组展示字段名、真实值、单位、来源、抓取时间和许可。
- 支持展开查看原始请求参数和返回摘要。
- 数据源失败时该组显示“暂未获取”，不提供占位值。

### 6.4 我的完成

- 首次进入为空状态，不预置任何完成记录。
- 列表只包含用户真实点击“完成打卡”的记录。
- 每条记录包含日期、挑战标题、规则 ID 和完成时间。
- 顶部统计“本月完成”“连续完成”“今日完成”，全部由真实记录计算。

### 6.5 位置与数据源

- 支持手动搜索城市并保存，也支持系统定位。
- 定位权限被拒绝时保留用户手动选择的城市，不自动使用 IP 猜测位置。
- 不保存精确经纬度，只保存城市名、时区和近似坐标用于天气查询。
- 数据源健康页展示每个接口的 `ok / stale / error` 状态与最近抓取时间。

### 6.6 部分可用降级

- 天气不可用时隐藏“降雨概率”“UV”等天气依赖建议，但保留空气质量与农历。
- 空气质量不可用时隐藏 AQI 相关建议，不生成“开窗通风”等依赖字段的建议。
- 全部数据源不可用且无当日缓存时，显示空状态“今日数据暂未获取”，并提供重试。
- 当日缓存存在时展示缓存并标注 `cachedAt`，缓存也算真实数据。

## 7. 规则引擎设计

规则引擎是后端纯函数，输入为真实数据字段，输出为确定性的签文集合。同一位置同一天重复调用结果一致。

### 7.1 输入字段

```text
date, timezone, city, lat, lon
weather_code, temperature_2m_max, temperature_2m_min, precipitation_probability_max,
uv_index_max, sunrise, sunset, daylight_duration, wind_speed_10m_max, humidity
european_aqi, pm2_5, pm10, ozone
lunar_date, solar_term_today, solar_term_tomorrow, holiday_name, is_weekend
```

### 7.2 灵感色映射

| 真实条件 | 颜色名称 | 色值 |
| --- | --- | --- |
| 降雨概率 >= 40 且 AQI <= 50 | 雨雾青 | `#2f9b8f` |
| 天气晴且 UV >= 6 且 AQI <= 50 | 晴空蓝 | `#4b8bff` |
| 多云且 AQI <= 100 | 云灰蓝 | `#7c93b5` |
| 降雪 | 初雪白 | `#e6f1ff` |
| AQI > 100 | 透氧橙 | `#e59a3a` |

映射表版本化，同一版本下结果稳定。

### 7.3 建议规则示例

| ruleId | 触发条件 | 建议文案 |
| --- | --- | --- |
| `ventilate` | AQI <= 50 | 开窗透气 15 分钟 |
| `walk-umbrella` | 降雨概率 40-70 且最高温 <= 35 | 带伞散步 20 分钟 |
| `hydrate` | 最高温 >= 30 或湿度 >= 70 | 今天喝够 6 杯水 |
| `uv-protect` | UV >= 6 | 10 点后外出记得防晒 |
| `solar-term-eve` | 明天是节气 | 给这个节气做一个温柔收尾 |
| `workday-write` | 工作日且非节假日 | 写下今天最重要的一件小事 |
| `holiday-greet` | 今天是节假日 | 给重要的人发一句问候 |
| `sky-photo` | 降雨概率 >= 40 或天气为晴 | 拍一张今天的天空 |
| `daylight-encourage` | 白天时长可用 | 白天 13 小时 32 分，足够完成最重要的一件小事 |
| `air-encourage` | AQI 可用 | AQI 37 优，开窗换气是对身体的小礼物 |

规则文案由人工维护、版本化，运行时只做“真实数据 + 模板”填充，不使用 AI 生成。

## 9. 真实数据方案

### 9.1 数据源

| 数据源 | 用途 | 说明 |
| --- | --- | --- |
| Open-Meteo Forecast API | 天气、温度、降雨概率、UV、日出日落、白天时长 | 无密钥，支持按经纬度查询 |
| Open-Meteo Air Quality API | AQI、PM2.5、PM10、臭氧 | 无密钥，实时空气质量 |
| lunar-go 等开源农历算法库 | 农历日期、节气 | 计算结果可复现，展示时标注来源 |
| 版本化节假日表 | 法定节假日、调休 | 人工核对国务院/官方发布，记录更新时间和来源 |
| 用户位置 | 城市与坐标 | 手动选择或系统定位，不保存精确坐标 |

### 9.2 数据管道

1. 后端按 `date + lat + lon` 调用真实接口。
2. 校验返回字段非空、单位正确、日期一致。
3. 将校验后的字段写入当日缓存，保留 `fetchedAt` 与 `source`。
4. 规则引擎读取真实字段生成签文。
5. 前端只展示已校验字段，缺失字段显示“暂未获取”。
6. 当日缓存存在时优先使用缓存，并展示 `cachedAt`。

### 9.3 AI 边界

允许：

- 使用规则引擎做条件匹配。
- 对真实字段做单位转换和友好展示。
- 把版本化文案与真实数据组合成签文。

禁止：

- 用 AI 生成“今日运势”“宜忌”“命理”或随机签文。
- 在数据源失败时用 AI 编造缺失字段。
- 把用户完成记录、位置或习惯用于生成个性化命运结论。

## 10. 接口设计

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/daily-luck-sign?lat=&lon=` | 获取今日签文，默认使用登录用户设置的位置 |
| GET | `/api/v1/daily-luck-sign/health` | 各数据源健康状态 |
| GET | `/api/v1/daily-luck-sign/history` | 用户真实完成记录 |
| POST | `/api/v1/daily-luck-sign/completions` | 记录一次完成挑战 |
| DELETE | `/api/v1/daily-luck-sign/completions/{id}` | 删除一条真实完成记录 |
| GET | `/api/v1/daily-luck-sign/settings` | 获取位置与展示设置 |
| PUT | `/api/v1/daily-luck-sign/settings` | 保存位置与展示设置 |

说明：

- 未登录用户可查看今日签，但完成记录只保存在本机。
- 登录用户完成后自动同步到账号。
- 所有响应字段带 `source` 与 `fetchedAt`。
- 服务端校验经纬度范围、日期格式和文案长度，不接受伪随机参数。

## 11. 视觉与交互

- 沿用 FunBox 现有浅蓝画布、白色卡片、深色文字、品牌蓝主色体系。
- 本功能增加低饱和青绿 `#2f9b8f` 作为特色色，避免与既有工具主色冲突。
- 内容区最大宽度 430px，宽屏居中；320px、390px、430px 视口均不允许文字溢出或元素重叠。
- 灵感色卡片使用大色块 + 色值 + 依据，不依赖渐变背景表达“运气”。
- 完成打卡、数据明细、来源展开、位置选择均为原生控件或明确图标按钮。
- 深色主题沿用现有 `appTheme.dark`，颜色映射表不改变，只在渲染层适配。

## 12. 状态与异常处理

| 场景 | 处理 |
| --- | --- |
| 首次进入且无位置 | 空状态“请选择城市或开启定位”，不生成默认签文 |
| 单个数据源失败 | 隐藏依赖该源的建议，展示其余真实字段 |
| 全部数据源失败且有当日缓存 | 展示缓存并标注 `cachedAt` |
| 全部数据源失败且无缓存 | 显示“今日数据暂未获取”和重试按钮 |
| 用户完成打卡 | 写入真实完成记录，首页按钮变为已完成 |
| 数据字段缺失 | 该字段不显示，不补造“暂无数值”以外的占位 |

## 13. 技术方案

- 前端新增 `frontend/features/tools/daily-luck-sign-screen.tsx`，复用 `MobileScreen`、`PageHeader`、`SurfaceCard`、主题 Hook。
- 规则引擎独立为 `frontend/lib/daily-luck-sign-rules.ts`，纯函数、可测试。
- 本地存储独立为 `frontend/lib/daily-luck-sign-storage.ts`，Web 与 Native 各一份实现。
- 后端新增 `backend/internal/dailylucksign/` 模块，包含数据拉取、缓存、规则引擎和完成记录。
- 节假日表与文案库作为版本化 JSON 放入仓库，禁止运行时从聊天生成。
- 新增 Node 测试覆盖规则映射、异常状态、存储与 UI 关键逻辑。

## 14. 一期验收标准

1. 首次进入且未设置位置时为空状态，不出现任何默认城市或默认签文。
2. 选择真实城市后，10 秒内返回由真实数据生成的完整签文。
3. 同一位置同一天重复请求结果一致，不使用随机数生成签文。
4. 首页每一个数值字段都能进入数据明细并查看 `source`、`fetchedAt`、`license`。
5. 天气或空气质量失败时，依赖该字段的建议被隐藏，不补造。
6. 完成记录初始为空，只有用户真实打卡后才出现。
7. 灵感色、小事、挑战、鼓励、数据明细、我的完成、位置设置、降级状态均一期上线。
8. 320px、390px、430px 视口无文字溢出和元素重叠。
9. Go 测试、前端 Node 测试、TypeScript 检查与 lint 全部通过。

## 15. 明确不做

- 不做吉凶、宜忌、命理、塔罗、星座运势等预测内容。
- 不做随机抽签、随机任务或随机“好运指数”。
- 不用 AI 生成签文、鼓励语或缺失数据。
- 不做无来源的“幸运数字”“幸运方位”“幸运物品”。
- 不做医疗、健康、饮食干预建议，所有内容均标注为轻娱乐灵感。
- 不保存精确定位，不生成个人命运画像，不做跨用户分享排行。

## 16. 风险与决策

| 风险 | 决策 |
| --- | --- |
| 用户期待真正的“运势预测” | 首页和注册描述明确“不测吉凶”，用可解释数据建立信任 |
| 天气源偶尔不可用 | 字段级降级 + 当日缓存 + 明确状态 |
| 节假日表可能滞后 | 版本化人工核对表，标注来源和更新时间 |
| 规则文案可能显得说教 | 文案短、轻、可关闭，挑战全部可选 |
| 颜色映射被质疑 | 展示 `ruleId` 和原始条件，规则版本可追踪 |
